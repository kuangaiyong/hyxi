## Facebook 评论区有三处折叠，和正文那个「展开」是两回事

`expandBodies()` 点的是**正文**折叠，只认 `^(展开|See more|Meer weergeven)$`。
评论区另有两类按钮，它一个都碰不到：

- **「查看更多评论」** —— 首屏每条主贴只渲染前两三条评论，其余藏在后面，**而且分页**：
  点一次只多出一页
- **「查看 N 条回复」** —— 一条评论底下的嵌套回复

**漏采的样子（真实库实测，src_b32bc603）**：79 条主贴的回复数分布
`{1条:17, 2条:30, 3条:5}`，**上限死死卡在 3、一条都没超过**。这不是自然分布，
是首屏渲染上限的指纹 —— 用户报的「只采到 3 条、实际应有 4 条」正落在这个天花板上。
回复采不全，舆情就少统计一份声音，而页面上完全看不出少了什么。

修在 `expandComments()`（v1.11.0），四条要点，改它之前逐条对一遍：

1. **按文字认，但不能精确匹配** —— 这些文案里带条数（「查看 2 条回复」），每条帖子都不一样
2. **必须挡住动作按钮**：每条模式要么带「查看/更多/weergeven/bekijken」，要么带一个数字。
   光是「回复」两个字不能匹配 —— 误点「分享」会弹对话框，误点「回复」会打开输入框
3. **要循环点到不再增长**（评论分页）。**一轮只点一个折叠**（理由见下面 ⛔ 那一节），
   两轮之间 `FOLD_CLICK_DELAY_MIN/MAX`（0.8~2 秒）：点「查看更多评论」是页面内的轻动作
   不是翻页，用翻页的 4~11 秒逐帖展开一批就要好几分钟；仍然随机、仍然不为零。
   轮次上限 `COMMENT_FOLD_ROUNDS`（30），**撞上限必须打日志** —— 静默停在半路等于又一次
   少采，而这回连日志都不提
4. **界面语言由 Facebook 账号自己的设置决定**，与采集器 locale 无关，中英荷三种都要收

**按钮不是 `div[dir=auto]`**（真实库 171 条正文没有一条带 UI 文案尾巴，实测核对过），
所以 `commentText()` 碰不到它们，`bodyTrail` 不需要为此扩充。改 fixture 时别把它们
做成 `dir=auto`，那会复刻出一个真站上不存在的问题。

### 三条只有实测才发现的坑（v1.11.0 发版前评审）

- **`expandComments()` 必须排在 `expandBodies()` 之前**。被「查看更多评论」加载出来的
  长评论，它自己的正文也折叠着；反过来的话，点正文「展开」那一轮它还不在 DOM 里，
  等它出现本批已经没人去点了。残文剥掉「… 展开」后看起来就是一句完整的话，照样入库。
  **可见部分超过 100 字时这是永久的**：指纹只吃正文前 100 字，截断版和完整版同一个
  指纹，下一批就算展开了也会被 `seen` 当成已见过丢掉。实测：入库 115 字，换顺序后 232 字
- **嵌套回复的 id 认 `reply_comment_id`，不认 `comment_id`**。回复的固定链接是
  `?comment_id=<所属顶层评论>&reply_comment_id=<自己>`（2026-09-13 真站核实，不论第几层）。只认
  `comment_id` 就拿到父评论的 id：**message_id 撞车 → 入库按 id 归并 → 父评论那一行的
  作者和正文被回复整条覆盖**，回复自己的指纹进别名表、永远不会再下发。时间锚点的标记
  也由 id 派生，回复连时间都继承父评论的。fixture 实测过：Joost 的评论整条消失，
  那一行成了「Ruud 的正文 + Joost 的时间 + Joost 的指纹」。`comment_id` 的匹配要求前面
  是 `?` 或 `&`，否则参数顺序反过来时会从 `reply_comment_id=` 里半截匹配出来
- **折叠文案还有「某某 已回复 · N 条回复」这种带前缀的写法**，以及英文的
  `View more replies` / 大写开头的 `2 Replies`。实测旧模式漏掉 7 种写法，其中
  「Joost 已回复 · 2 条回复」是中文界面就会遇到的。模式与 `i` 标志都放在
  `SELECTORS.commentFoldText` / `commentFoldFlags` 里，`expandComments()` 和回归测试
  `TestCommentFoldPatternsEndToEnd` 都从那里取，别各写一份

回归由 `test_folded_comments_are_expanded_before_extraction` 守（真 Chrome +
`login_site.py` fixture，折叠故意分两页，专门钉「点一次就收工照样漏」）。

### ⛔ 有的折叠会把页面带进帖子详情 —— 留在那儿，整轮采集就只剩一条帖子

**这是 v1.11.0 引入、v1.11.4 才修掉的回归，也是最贵的一课。**真站实测（2026-09-13，
用户那份数据）：

| 版本 | 折叠日志 | 那一批提取到 |
|---|---|---|
| v1.11.0 | 点开评论折叠 2 处 | **1 条** |
| v1.11.2 | 点开评论折叠 12 处 | 8 条 |
| v1.11.3 | 点开评论折叠 2 处 | 11 条，紧接着「页面不再增长，已到底」 |
| **不点任何东西**的只读探针 | — | 首屏 9 条主贴，滚 8 次到 **45 条** |

「11 条」正是**一条主贴 + 它十来条评论**。一次性把整屏的折叠全点了，其中某个
「查看更多评论」没有就地展开，而是把帖子详情整个打开 —— 这一批就只提取得到那一条，
信息流也滚不动，`scrollOnce()` 于是判「已到底」。那条主贴的回复数确实从 2 变成了 6，
**代价是整轮采集只剩它**。

v1.11.4 的修法是「退回信息流 + 这条主贴整轮拉黑」—— **信息流保住了，这类主贴的隐藏评论却在
任何一轮都采不到**（同一个按钮每一轮都是同样的行为，「下一轮再补」不成立）。用户随即报了
「原帖 6 条只采到 1 条」。v1.12.0 查明真站的行为并改成就地收割，见下一节。

### 帖子浮层：就地收割、逐级关闭（v1.12.0，2026-09-13 真站只读探查）

**真站实测**（修复文档 `docs/fixes/2026-09-13-facebook-thread-incomplete.md` 有原始记录）：

- 点「查看更多回答 / 评论」= **pushState** 到 `/groups/<gid>/permalink/<id>/` + 弹 `[role=dialog]`，
  浮层内容随后由 XHR 取回；点浮层「关闭」（aria-label）后 URL 回到信息流、卡片还在、**没有重载**
- 浮层**盖住信息流**（信息流 DOM 还在后面）：浮层开着时信息流里的元素 hover 不到，
  浮层里的 hover 必须限定在浮层内（`hoverTime` 的 scope），否则 `page.$` 先找到后面被挡住的那个
- 浮层里主贴头部**没有** `/posts/<id>` 链接 —— 浮层开着时提取信息流，它就成了一条没 id、
  没时间的新主贴（真实库「Hugo van Touw」那条的来路）。所以信息流提取排除 `[role=dialog]` 里的 article，
  存量由 `merge_duplicate_posts()` 按「作者 + 正文逐字相同、只对上唯一一条」并掉
- 卡片上的评论数按钮：文字「6」、aria-label「发表评论」，**含回复的回复**
- 直接打开固定链接是**首页信息流上盖一层同样的浮层**，背景是别的帖子 —— 只从浮层里取

**流程**（`expandComments()`，改之前逐条对一遍）：

1. **一次只点一个折叠**，点完 `afterFoldClick()` 判四种结果：`dialog` / `moved`（整页被带走）/
   `grew`（就地展开）/ `stale`。真站是先换地址、内容后到，地址是 `/permalink/` 的要多等浮层
2. `dialog` → `harvestThread()`：**先核对浮层地址里有这条主贴的 id**（对不上不收 —— 挂错主贴比少采
   糟得多；**按路径段比**，真站地址有的不带末尾斜杠，2026-09-15 实测 `/permalink/2476737042802015`，
   拿 `/<id>/` 去比会把它自己的浮层判成对不上、退到固定链接整页补），**再等评论条数稳定下来**（`waitForThreadSettled()`：浮层内容是 XHR 取的，一出现主贴就收，
   折叠一个都还没渲染，会被记成「整串读完」。等到头浮层里还是只有主贴时看卡片：卡片上也一条没露的，是原帖
   确实看不到评论（删了没减数），照常收空串记读完，否则每轮都白开一遍；卡片上露过评论的就是没加载出来，
   不收、留给固定链接补），然后展开浮层里的折叠、提取、取时间；
   `harvested`（模块级）存整串，卡片提取时顶替。找「开着的浮层」一律要求可见（`getClientRects()`），
   关掉后藏起来的旧浮层排在文档前面，不查可见性就会点到它身上
   · 判「就地展开了」只数**这条主贴自己**的 article：数整页的话信息流懒加载进一条新帖就算成展开成功，
   同一个没用的折叠被反复点到轮次上限
   · **收割出错只放弃这一串**（`expandComments` 里的 try/catch）：浮层里页面调用失败（整页跳转销毁了
   上下文之类）照样关浮层接着采。冒到 main 的话首轮直接硬失败，而这条主贴每轮再点、再失败；浏览器没了照样抛
3. **关浮层逐级退**（`closeThreadDialog()`）：关闭按钮 → Esc → 后退（地址没变过就不许后退，那会
   退出小组页）→ 重新载入信息流并在日志说明。**绝不能留在浮层上**。真站（2026-09-15，v1.12.0 全量
   78 个浮层）走到「重新载入」1 次，正是上面那个不带斜杠的地址，原因没查明；重载后已采的整批重滚回来、
   每批十来秒，本轮照常跑完
4. 原帖评论数读得到时，`siteCount ≤ max(卡片已有, 库里已有)` 的不点。「库里已有」由 Python 按主贴
   message_id 下发（`known_comment_counts`，全量重跑时清空）= max(整棵子树条数, `harvested_site_count`)：
   - **只数子树不够**：被「最相关」藏掉的、删了没减数的评论浮层里永远看不到，条数永远对不上，
     每轮增量都会把这串再开一遍
   - **不能拿 `site_comment_count` 顶**：上一轮没补成（到了时限、浮层没弹）的也记着原帖数，那样就再也不补了。
     `harvested_site_count` 只在「浮层里折叠点到一个不剩、每条评论的时间都取到了」（`harvestThread` 的
     `complete`）才记 —— 时限跳过和 tooltip 没出来都算没读完，否则原帖数不涨就不再打开，时间永远是空的
5. 卡片上没有折叠可点、或点了没收成的，**本轮信息流滚完后按固定链接补**（`completeFromPermalinks()`），
   只补原帖评论数读得到且对不上的；卡片上已输出过的几条层级以整串为准改写。**某一条打不开只跳过这一条**，
   限流（`err.blocked`）和浏览器没了照样往外抛
6. 采集时限：runner 下发 `deadline_at`（超时前留 3 分钟，短超时最多让 20%），过点不再开浮层、
   不滚动、不补齐、**不再 hover 取时间**（一条最多等好几秒），按退出码 2 交出已采到的 ——
   runner 到点是直接杀进程，交接文件没写就一条不剩。**限流退让也不许睡过时限**：`gotoPage` 照 Retry-After
   最多睡 5 分钟、比余量还长，调用处传 `CONFIG.deadlineAt`，要睡过时限就当场按拒绝访问（`err.blocked`）停下
7. **两个数走 `thread_counts`，不走帖子**：脚本输出里按主贴 message_id 带 `site_comment_count` 与
   `harvested_site_count`，runner 在 upsert 之后调 `storage.record_thread_counts()`。增量运行时老主贴
   指纹见过就不再输出，只靠帖子带的话原帖数停在第一次采到时 —— 涨了之后这轮又没补齐，结果页照样
   「已采 6 · 原帖 6」不标黄，正好把不全藏起来
8. **不点评论排序菜单**：「评论排序方式将应用于 Facebook」，是账号级设置；只把当前排序记进日志

### 回复的层级（`extractInPage` 里的 `threadOf`，卡片与浮层共用一份）

浮层里回复**不嵌在**父评论 article 里，全是主贴 article 下的兄弟节点，层级只体现在缩进（真站
418 / 479 / 521px）。链接：评论 `comment_id=<自己>`，回复不论第几层都是
`comment_id=<所属顶层评论>&reply_comment_id=<自己>`。算法：

1. DOM 上嵌在某条评论 article 里的，直接认那一条（fixture 9001 的卡片形态）
2. 否则是回复（链接带 `reply_comment_id`）的，认文档顺序里前面最近一条**缩进更小**的（栈）
3. 最后拿 `comment_id` 校验：顺着父指针走到头的那一条，它「所属的顶层评论」（评论是它自己，回复看
   它链接上的 `comment_id`）得和链接一致。对不上以链接为准挂到那条顶层评论下，**那条没采到（折叠没点完、
   被「最相关」藏掉）就挂主贴** —— 按缩进猜的那条已知不是它回复的，挂上去就是「回复挂错人」。
   比「所属顶层评论」而不是比 id：挂了主贴的那条回复，它自己的回复链接上也指着那条没采到的，
   按 id 比会被判不一致、跟着一起拍平。不一致计数进日志「层级与链接不一致 N 处」——
   Facebook 改成用内层元素缩进时，这个数会暴露算法失效

`flattenComments()` 按父指针写 `parent_fingerprint`，`reply_level` 沿父指针数。**不是一律挂主贴、
第 1 层** —— 那样写了好几个版本，还有一条测试把它断言成「存储层扁平」的正确行为。aria-label
（「X回复了Y的回复」）写得最明白，但随账号界面语言变，只当参考不当判据。

**fixture 的形态**（`login_site.py`）：9001 就地展开（卡片嵌套形态）；9004 点「查看更多回答」弹浮层，
浮层里 L1/L2/L3 兄弟节点 + 浮层内还有一处折叠（**卡片上露的是 5606，5601–5605 只在浮层里** —— 写「没收割成」
的断言时拿 5606 当卡片那条，别凭印象写 5601：旧代码往往更早就失败了，红测时暴露不出来）；9005 没有折叠、走固定链接（卡片上露 5701，5702–5704 只在固定链接页上），5704 的链接与缩进故意
对不上；9006 的折叠整页跳走（真站没见过，守退路）；9007 的折叠错开到信息流里没有的 9008 的浮层；
`sticky_dialog=True` 时浮层三种方式都关不掉；`permalink_failure="network"/"blocked"` 时固定链接断开 /
回 403（Retry-After 秒数取 `permalink_retry_after`）；`broken_dialog` 9004 的浮层里一查 article 就抛错；`slashless_thread_url` 浮层地址不带末尾斜杠；`hidden_comments` 可在两轮之间改，9004 / 9005 的原帖数多出几条而浮层里看不到；
`stale_dialog_fold` 浮层里的折叠点了不加载；`deferred_thread_comments=N` 浮层先只有主贴、评论 N 毫秒后才到
（负数永远不到）；`hidden_stale_dialog` 页面最前面藏着一个旧浮层；`dead_fold_card` 多一条折叠只让信息流变长的
主贴 9010；`ghost_comment_card` 多一条原帖 1 条评论却哪儿都看不到的主贴 9011；`tipless_reply` 5603 取不到时间；
`thread_requests` 记浮层接口 / 固定链接 / 折叠 / 关浮层方式（`close:button`/`close:esc`），
是「这一轮有没有去打开帖子」唯一的观测点。
**fixture 编码的是我们对真站的假设**：浮层内折叠、Esc / 后退能关、5704 那种错位都是假设，
交付前必须跑一轮真站（看的是那条主贴采到几条、层级对不对）。

### 滚动到底的判定

`scrollOnce()` 曾经是「滚一次 + 等 2.5 秒 + 比高度」，v1.11.3 改成分几次「推一把」+
轮询等增长（`SCROLL_NUDGES` × `SCROLL_GROWTH_MS`）。**当时以为「已到底」是懒加载比
2.5 秒慢造成的 —— 这个判断是错的**：放宽到 12 秒后真站照样在第一批就「已到底」，真因是
上一节的详情页。只读探针也证实 `window.scrollTo()` 本身就能触发加载（4466 → 8118 →
11823）。放宽等待本身无害（等待期间不发任何请求），所以保留，但**别再把「已到底」
归因到等待时间上**。

复刻懒加载的 fixture 有几条硬要求，写测试前先看，否则测出来是空转的（都实测踩过）：

1. **页面要够高**（`#spacer` 8000px）。不够高时 `window.scrollTo()` 压根不产生
   scroll 事件；更隐蔽的是 —— 每批开头的 `humanRead()` 会滚 2~4 次、每次 300~900px，
   页面只有一两千像素的话它自己就滚到底了，懒加载的内容在**提取过程中**就插进来，
   `scrollOnce()` 反而量不出增长，于是**旧代码也能通过**
2. **懒加载只在真滚到底时触发**（`scrollY + innerHeight >= scrollHeight - 50`），
   理由同上
3. `TestFacebookLoginEndToEnd._run()` 默认 `max_batches=1`，验第二屏的用例必须传 2

## 正文图的抓取（tweakers + facebook_group）

**图片字节取自浏览器自己的响应，不再二次回源。** `collectors/lib/media.js` 是唯一实现，
两个采集器共用；`group_feed.js` 没有图片能力（它只服务本地 fixture）。

- **`context.request` 是 Playwright 在 Node 进程里自带的 HTTP 客户端，不是 Chrome。**
  实测（2026-08-21）它连 `Sec-Fetch-Dest` / `Referer` / `sec-ch-ua` 都不带，更**不读系统
  代理** —— `playwright-core` 整个包里 `HTTPS_PROXY` 出现 **0 次**，`browser.js` 也从没给它
  传过 `proxy`。于是「Chrome 走系统代理把图显示出来了、脚本直连回源却连不上」是一个完全
  可能的状态：**页面抓得到、帖子入库了、图一张都没有**。用户实测报过，而开发机跑的 fixture
  打的是 `127.0.0.1`、代理对 localhost 一律不生效，所以旧实现**在测试里永远是绿的**
- 现在 `attachImageCapture(page)` 挂 `page.on('response')` 把图片响应体留下来，
  `saveImages()` 直接写盘。**必须在任何导航之前挂**，晚一步第一屏的图就漏了。
  顺带把图片请求数从「页面加载一次 + 回源一次」减半，与反爬虫姿态一致
- **缓存读了不删**（同一张图可能配在两条帖子上），内存由 64MB 总量上限 + FIFO 驱逐兜住。
  覆盖同一个键前必须把旧字节数减掉 —— `bytes` 一旦漂过上限，驱逐循环每插一张就把整个缓存
  清空一次，所有图片于是**静默**退回回源那条路，正是要摆脱的那条
- **按重定向链建别名**：图片被 302 时 DOM 上的 `src` 是原始 URL、`response` 报的是最终 URL，
  不建别名命中率直接归零
- 回源仍保留作兜底（懒加载没触发、或直接命中 Chrome 内存缓存因而没有 response 事件），
  **两次回源之间的 300ms 间隔不能去掉** —— 请求节奏是反爬纪律
- **两个阶段都必须出声**。「页面上就没有图」「选择器没选中」「被尺寸门限挡了」「下载失败」
  以前在日志上长得一模一样：什么都不显示，这正是这个问题拖到用户那边才暴露的原因。现在
  提取阶段报候选/命中/排除原因（含被排除图的 host 与渲染尺寸），下载阶段报真实报错原文
  （`ECONNREFUSED` / `ETIMEDOUT` / `407` 指向完全不同的处置），跑完再来一行
  `图片汇总：候选图片地址 N 个 · 通过筛选 N 个 · 落盘 N 张…`
- **汇总里前两个数按 URL 去重、后两个是文件数**，措辞必须区分：信息流每一批都会把上一批的
  帖子重新提取一遍，逐批累加的话 10 批下来会虚报出 82% 的假丢失率 —— 而这行恰恰是远端
  出问题时唯一的诊断依据，它自己说谎就白做了
- **Tweakers 侧的选择器 2026-09-19 已在真站核对过**（真 Chrome 打得开，见 CLAUDE.md
  「反爬虫姿态」末尾那条）：正文图在 `tweakers.net/i/<sig>/x800/…`，渲染 369×800 ~ 800×600；
  表情是 `tweakers.net/g/s/*.svg`，16×16 / 34×16 / 30×17。所以那边**仍然不设 host 白名单**
  （站点换域名就全瞎），只按「在正文容器内」+「非 `data:` URI」+「渲染尺寸 ≥ 80」筛，
  80 这条线两边都留了足够余量，剩下的交给日志。三个坑已经踩过并钉住了：
  **尺寸必须在原始元素上量**（剥引用块用的那个 `cloneNode` 游离于文档之外，
  `getBoundingClientRect()` 一律返回 0，照着 clone 取会把每张图都过滤掉）；
  **取图的容器要跟着正文走**（没有 `.messagecontent` 时正文来自 `.post`，盯死前者会让这条
  路上的帖子静默丢图）；**引用块里的照片不是 `<img>`** 而是一个
  `<a href="…原图…">[Afbeelding]</a>` 锚点，浏览器根本不会请求它 —— 得建游离的 `Image`
  把它拉进来，否则它只能走回源那条路，而那条路一轮连打十几次会被 WAF 403（实测 16/35 张）
- **页面上的图必须让浏览器自己取**：真站实测不滚动时一页 100 层楼只有 1 张正文图被加载，
  其余全落到 `context.request` 回源。`tweakers.js` 的 `loadLazyImages()` 因此把整页滚一遍
  （步长 1200px、120ms），滚完 13/13 张由浏览器加载。这既是「不缺失」，也把
  「页面加载一次 + 回源一次」减成「只加载一次」，与反爬虫姿态一致
- 回归测试：`TestFacebookLoginEndToEnd::test_images_survive_when_only_the_browser_can_fetch_them`
  让 fixture 服务器**按真实请求头**把非浏览器发起的图片请求一律 502，忠实复刻用户那台机器的
  状态（真服务器、真 Chrome、真子进程，无 mock）；
  `TestTweakersCollectorGoldenEndToEnd::test_body_images_are_downloaded_and_quoted_ones_ignored`
  钉住引用块、表情、跨页同 URL 去重。**`golden_tweakers.json` 那条基线同时保证指纹没动** ——
  `<img>` 不贡献 `textContent`，正文一个字符都不能变，否则历史帖子全被判成新帖重新付费翻译


## 全量重跑（`force_full`）

`POST /tasks/{id}/retry?full=true` 复用原描述建一个新任务，并把 `tasks.force_full`
置位。执行时 `execute_task()` 一次性放开**三处**增量判据：

| 步骤 | 平时的增量判据 | force_full 时 |
|---|---|---|
| collect | `params.incremental`（默认 True） | 置 False |
| translate | `_processed.translated` | 全部当待翻译 |
| sentiment | `_processed.sentiment_at` | 全部当待分析 |
| 图片理解 | `posts.image_desc` 非空即跳过 | 内存里清空，全部重新理解 |

- **`force_full` 必须是 tasks 表的真列**：那张表是固定列表，任务字典里的自定义键
  根本不会被持久化，服务重启或从库里读回时就丢了。补列走 `PRAGMA table_info` +
  `ALTER TABLE ADD COLUMN`（同 `_ensure_posts_image_desc`）
- **关掉增量时必须一并清空 `known_fingerprints` 和 `max_page_number`**
  （落在 `CollectorRunner`）。`facebook_group.js` 的 `seen` 集合是**无条件**用
  `known_fingerprints` 建的（只有水位线提前退出那句看 `incremental`），照旧下发的话
  每条帖子都被判成「见过」→ 不进 `fresh` → **配图也不会重下**，于是 `incremental=False`
  对它完全无效。回归测试见 `TestFullRerunDropsIncrementalAnchorsEndToEnd`
- **`image_desc` 也必须一并放开**（清在 orchestrator 的 sentiment 分支）。它平时与
  `translation` / `sentiment_at` 同规矩「绝不重算」，而 `sentiment_service` 跳过的判据
  正是「已经有 image_desc」—— 不清掉的话，用户为「按当前口径重算一遍」付了钱，图片
  描述却仍是旧模型的产物，而**换了多模态模型正是有人点这个按钮的主要原因**，界面弹窗
  也白纸黑字承诺了「带图的还会再调一次多模态模型」。只清内存那一份：`save_image_descs()`
  不写空串，所以多模态没配 / 这一张没描述出来时，库里旧描述仍在，下一轮照常读回。
  回归测试见 `test_full_rerun_also_re_describes_the_images`（含「普通重跑不得重复付费」的对照组）
- **新建任务和定时任务一律走增量**，只有那个按钮给 True —— 否则每一轮定时都在重复
  付翻译和舆情的钱
- 界面上必须二次确认（`TaskManagementView` 的弹窗），并在任务行挂「全量」徽标：
  两条描述一样的任务摆在一起，没有它就分不出哪条重译过

**连带的一条存储规矩**：`upsert_posts()` 的 UPDATE 分支**只在本轮真抓到图时才覆盖
`images_json`**。写死成「采集到什么就是什么」的话，全量重跑撞上一次网络抖动就会把它
写成 `[]`，而图片文件还好端端躺在 media 目录里 —— 页面上整批消失且毫无提示。
与旁边 `translation` / `image_desc` 「绝不被采集冲回空值」是同一套道理。

## 老帖新回复（避免被时间倒序埋掉）

出口一律「主贴按发表时间从新到旧、评论跟着自己的主贴走」（见上一节），副作用是
**今天发在两个月前主贴上的回复，会被排到两个月前的位置去**。真实数据实测：163 行的
报告里，4 条这样的回复落在 #68 / #133 / #134 / #147，三条都在报告底部。

判据只有一份，在 `post_tree.mark_fresh_replies()`，理由同 `order_by_thread()` ——
导出和结果页共用一条规则，各写各的迟早分家。

**页面上的展示只在「任务结果页」**（`ResultsView.vue`）：一个「🔥 只看新回复」开关
加 3/7/14 窗口选择。舆情页那套面板与开关已整体拆除，只留了一个窗口选择器紧贴导出按钮 ——
它决定**报告**里「近期新回复」工作表和「更新提醒」列用哪个窗口，而导出入口全站只有那一个。

- **筛选必须在服务端做**（`/posts?only_fresh=true`）。一页只有 50 个主贴，而新回复恰恰
  因为主贴按时间倒序被压在后面几页 —— 那正是这个功能要解决的问题，在前端筛只能筛出
  当前页里的，等于什么都没做。舆情页那版能在前端筛，是因为它把帖子全量拉下来了，
  结果页是服务端分页，搬不过来
- `only_fresh` 与 `search` 是 **AND**；`total` 在过滤之后算，否则分页器会显示出翻不到的页码
- **筛空时搜索栏必须照常渲染**（`ResultsView` 的 `hasFilter`）—— 它自己就是关掉
  筛选的唯一入口。整张卡片（搜索栏 + 列表 + 分页）本来一起挂在 `posts.length` 上，
  而空状态那块又要求 `!isCompleted` —— 于是已完成任务一旦「只看新回复 + 近 3 天」
  没命中，**整个查询区域连同开关一起消失**，只能刷新页面（用户实测报过）。
  搜索搜不到结果是同一个坑，只是没人点到。分页条则相反，空时**不能**渲染，
  否则显示成「第 1/0 页」

- **基准是数据集里最新的帖子时间**（`baseline_time()`），不是 `datetime.now()`。
  按 now 算的话，隔一阵子没采集、或翻看几个月前的历史报告时**一条都不会亮**，
  而那份报告当初想标出来的东西并没有变。报告要自洽、可复现
- **窗口 `FRESH_DAYS_CHOICES = (3, 7, 14)` 是封闭集合**，`_validate_fresh_days()` 拦非法值
  并返回 400，**不静默回落到默认值** —— 那样用户以为自己换了窗口，实际看到的还是 7 天
- **三条不标的边界**：主贴也在窗口内（整串都新，本来就排在最前面）；回复或主贴的时间
  读不出来（早期采集故意留空，「实际很新」是推测，宁可漏标）；父贴不在本批数据里
  （`build_tree()` 已把它按主贴处理，它就不是回复）
- Excel 新增「更新提醒」列 + 命中行整行暖色（`FRESH_FILL` **优先于** `REPLY_FILL`，
  两个底色叠在一起就都看不出来了），并新增工作表「近期新回复」，顺序是
  **概览 → 近期新回复 → 帖子明细 → 配图**（工作簿默认停在第一张，第二张最容易被看到）
- **聚焦表把主贴完整带上**：一条「你能通过 HA 控制它吗」脱离主贴根本读不懂在说什么，
  用户不该为了看懂一条新回复再去别处翻主贴。但**不带该主贴的其他旧回复** —— 热帖十几条
  全搬过来就长得没法一口气读完，末尾给一条跳转即可
- **明细表的排序一个字没动**。聚焦是新增入口而不是重排 —— 两个出口共用一条排序规则
  这条既定约束不能破
