# 邮件通知：把所选数据源近 N 天的新回复（和新主贴）发到邮箱

> 用户 2026-10-16 提的需求，同一天一起修了「只看新回复」窗口不单调的问题
> （`docs/fixes/2026-10-16-fresh-replies-not-monotonic.md`）—— 邮件里的「新回复」用的就是修好之后的口径。

## 需求（用户原话要点）

- 新增一个菜单，配置：收件人列表；数据源（可多选）；新回复时间（近 3 / 7 / 14 天，**不设置默认是当前时间的前一天**）；
  SMTP 服务器、端口、SSL 端口；发件人邮箱、用户名、密码
- 标题按所选数据源和时间窗口生成
- 正文显示新回复的原文和译文，参考任务详情的显示方式；**不要舆情、不要原文链接**；要体现数据源（如「来自 Facebook 公开小组」）；
  用 HTML 或表格
- 新回复超过 20 条时，以 HTML 文件作附件

## 用户的决定（2026-10-16）

| 问题 | 决定 |
|---|---|
| 「新回复」的口径 | 只看回复时间：近 N 天内发的回复都算，主贴新不新不管（同结果页，3 ⊆ 7 ⊆ 14） |
| 怎么发 | 手动「立即发送」+ 可选每天定时 |
| 新回复缺译文 | 发送前先补译；失败重试，最多重试 3 次；还失败就告知用户，这次不发 |

**v1.15.0：用户让我定的三项（2026-10-17，「你来帮我决定」）**

| 问题 | 我的决定 | 理由 |
|---|---|---|
| 采集之后、发送之前发表的回复会漏发 | **修**：窗口照旧按发表时间，另加补发 —— 没随哪封发送成功的邮件发出去过、发表在这个来源的补发起点之后的，这一封补上，标「补发：之前没发出」 | 通知最怕悄悄漏；采集 08:00、发信 09:00 时每天稳定漏掉一小时，采集间隔越长漏得越多；某一轮失败、服务停一天也一样 |
| 改口径后结果页 / 导出标「新回复」的地方变多 | **接受，不改** | 一个定义处处一致；真实数据没泛滥：便携包数据近 7 天被标 57 条，占 1076 条的 5%（近 14 天 101 条，9%），标签上的「主贴 N 天前」照样分得出老串新串 |
| 没有回复的新主贴不进邮件 | **加进来**，标「🆕 新主贴」，全文照登；它和新回复一样必须翻成才发 | 舆情工具：一条新发的负面帖没人接话，以前就哪封都不出现 |

## 设计

**配置**存 `app_config`：`notify.settings`（JSON）+ `notify.password_enc`（SMTP 密码密文）。最近一次发送的结果在
`notify_status.last` —— 不能挂在 `notify.` 下，`set_app_config` 按前缀整组覆盖，保存一次配置就会把记录删掉。

**选新回复**（`notify_service.collect_fresh`）：对每个所选来源调 `post_tree.mark_fresh_replies(posts, days, 平铺来源, base=现在)`。
判据与结果页「只看新回复」是同一个函数，只是基准不同：结果页用数据集里最新一帖（报告隔多久打开都自洽），
邮件用发送那一刻（定时摘要要的是「这段时间里有什么新的」）。不设置窗口按 1 天。Tweakers 平铺楼层按主题的回复算（`Collector.thread_kind`）。
时间戳不带时区，「现在」要先换到来源的时钟（`Collector.timestamp_tz`）：Facebook 是宿主机时间，Tweakers 是荷兰时间 ——
直接拿上海的现在去比，窗口整体偏 6~7 小时，每天有一段回复哪封都进不去（评审发现）。

**新主贴**（v1.15.0）：近 N 天发的顶层主贴，没有回复也算。判据是「没有父指针、且 `reply_level` 为 0」—— 丢了父贴的回复
也排在树根，但它不是主贴（同结果页徽标）。Tweakers 那种一源一串的来源不出新主贴：主题是用户挑好的那一条，而且只是采到的最早一楼。

**补发**（v1.15.0）：直接记「发没发过」，不拿时间反推。
- `posts.notified_at`：这条帖子（作为新回复 / 新主贴）随一封**发送成功**的邮件发出去的时间，没发过是 NULL。只在 SMTP 投递成功后写
  （作上下文的老主贴不记）；采集不碰它。老库补列后旧行是 NULL —— 升级前本来就没有邮件通知
- 补发起点 `notify_marks.anchors`：{来源: 起点}，起点 = 这个来源**第一次进邮件那一轮的窗口起点**，之后**一直不动**。
  单独一个前缀，写发送记录时不会把它冲掉；取消勾选的来源在保存配置时忘掉起点（再勾回来从那一刻重新算）
- 每一封 = 近 N 天的新内容（窗口照旧）**加上**：发表在起点之后、还没发过的回复和新主贴，标「补发：之前没发出」。
  采集晚了、某一轮失败、采集停了几天、改了天数、事后才读到发表时间，都落在这一条里 —— 起点之后发表的不会漏，
  补发过的也不会再补（它发出去就记了 `notified_at`）
- 窗口内的条目照用户定的窗口每封都列（窗口比发送间隔长时同一条会连着出现几封），前几封已经发过的标「已发过」，读的人好跳过
- 新加进来的来源从这一轮才开始，不补它之前的；起点记录坏了当作没有、就地重起（这一封不补发），不让每一轮都失败
- **补发的翻不成只放原文、照发**：按窗口挑出来的新内容才必须翻成（用户定的「失败就不发」），它们过了窗口会自己掉出去；
  补发的要是也拦邮件，就可能每轮都被挑出来、每轮都失败

为什么这么定：前两版都拿时间去推「这条发没发过」—— 先是入库时间，再是每轮挪动的水位线 —— 三轮提交前评审各找出几种漏法：
失败那一轮窗口里的内容进不去、改了天数算错、重复行合并绕过入库时间、补发没上界时一条拒译的帖子能把邮件永远堵死、
采集停摆比窗口长时「没有新内容」的那几轮把下界挪过头。每修一处就多一层特例；直接记「发没发过」、起点钉死之后这些一起消失，
`upsert_posts()` 这个红线函数也不用动。

**邮件内容**：按来源分节，标题「来自：<采集器显示名>「<来源名>」」；每个讨论串先放主贴（原文 + 译文，超过 600 字截断，
同结果页卡片的折叠长度）作上下文，再列新回复（作者、时间、原文、译文；第 2 层起写「回复 某某」）。
主贴按发表时间从新到旧（同结果页和导出），串里按发表先后。图片只给一行「含 N 张图片」，不附图。
新主贴的卡片标「🆕 新主贴」、全文照登（它是新内容本身，不是上下文）；补发的回复 / 新主贴标「补发：之前没发出」。
所选来源里没有新内容的写「近 N 天没有新回复和新主贴」，但**不进标题**（见下「证据」里的真实数据发现）。
计数分开写：「新回复 X 条、新主贴 Y 条」，标题、正文抬头、各节标题、发送记录都是这个说法。
样式全部内联（邮件客户端常剥掉 `<style>`），帖子内容一律 `html.escape`，换行还原成 `<br>`。
新内容（新回复 + 新主贴）超过 20 条：正文列**最新的** 20 条（结构不变、截过的那节标题注明「正文只列了其中最新的一部分」），
完整内容是一份能用浏览器单独打开的 HTML 附件。

标题：`【HYXi】<采集器显示名>「<来源名>」[等 N 个数据源] · 近 N 天 · 新回复 X 条、新主贴 Y 条`（为 0 的那项不写），
只点有新内容的来源。前缀不写「新回复」：只有新主贴的那天会自相矛盾（评审发现）；正文抬头是「HYXi 新回复 / 新主贴摘要」，附件名 `hyxi-digest-*.html`。
正文截取时没排进最新 20 条、只因为它的回复排进去才出现的新主贴，在正文里只作上下文（截断），全文在附件里。

**补译**（`_backfill`）：要显示的帖子（新回复、新主贴、作上下文的老主贴）里 `needs_translation()` 为真的，先用 `TranslatorService.execute` 翻，
写回 posts 表。翻完还有失败的就整轮再翻，最多再翻 3 轮（用户定的「最多重试 3 次」）；**新内容**（新回复、新主贴）仍有失败就不发，
`last.message` 写明几条、原因（取译者的第一条 warning，比如模型报的错）。**老主贴翻不成不拦邮件**：它只是上下文，一条总被拒译的老主贴
不能让每天的邮件都发不出去（评审发现）—— 邮件里它只放原文，发送记录里注明几条主贴没翻成。渲染判据同 `needs_translation`，
失败标记不会被当成译文放进邮件。
补译前先 `orchestrator.claim_translation` 占住来源 —— 与结果页补译、任务里的翻译步骤互斥，被占着就每秒重试（最多 30 分钟），
占到后先回库刷新译文（复用 `orchestrator._refresh_translations`）再算还缺哪些，别人刚翻好的不重翻。

**发信**（`deliver`）：`smtplib`。勾了 SSL 连 SSL 端口（`SMTP_SSL`）；不勾连普通端口，服务器支持 STARTTLS 就先升级。
证书用 `ssl.create_default_context()` 严格校验。错误翻成能照着改的人话：535 → 提示 QQ 等要填授权码；SSL 握手失败 → 端口和 SSL 对不上；
超时 / 连不上 → 带上 `host:port`。阻塞调用放进线程（`asyncio.to_thread`）。

**两个入口一条路**：「立即发送」（`POST /send`，后台作业，运行标记同步置上防连点）和每天定时（APScheduler job `notify-daily`，
回调 `notify_service.scheduled_send` 是模块级函数 —— job 存在库里，重启后靠「模块:函数名」找回来）。都走 `_run → _send_digest`。
同一时刻只跑一轮：手动撞上返回 409，定时撞上跳过并记日志。正在发送时「清除配置」也回 409 —— 那一轮手里拿着配置快照（连同密码），
清了照样会把信发出去，结束时还会把发送记录写回来（评审发现）。

**每天定时**跟着配置走：保存 / 清除配置时 `sync_schedule()` 挂上或摘掉；`SchedulerService.start()` 末尾也按配置重挂一遍
（坏配置只跳过自己，不拦调度器启动）。没有新内容的那天不发，记一条 skipped。

## 安全

- SMTP 密码 Fernet 加密落库，只进不出（同数据源凭据）；没配 `TWEAKERS_SECRET_KEY` 拒绝保存（400），不降级成明文
- **留空 = 沿用已保存的密码，只限 SMTP 服务器和用户名都没改**：换了服务器还沿用，等于把密码交给那台新服务器 ——
  能调接口的人就能从自己搭的 SMTP 上套出这个「只进不出」的密码
- 外部服务器既不走 SSL、又不支持 STARTTLS 时拒绝登录（密码不明文出本机）；本机回环地址上的中继除外（流量不出这台机器）
- 邮箱地址按发信时的规则校验（正则之外再过一遍 `email.headerregistry.Address`）：只过正则的话，`a[b]@c.d` 这种存得下、
  每次发送却都在组邮件时失败（评审发现）
- 证书严格校验，测试里靠 `SSL_CERT_FILE` 信任现生成的自签证书，被测代码里没有任何「不校验」的口子
- 用户在对话里给的 QQ 邮箱登录密码**没有使用、没有写进任何文件**：QQ 的 SMTP 要用授权码，而且替用户把别的服务的真实密码填进系统
  不在 Claude 的授权范围内。QQ 实发由用户自己在页面上做

## 已知限制 / 没做的

- **QQ 邮箱实发没验**：要用户的授权码。服务器 `smtp.qq.com`、勾 SSL、SSL 端口 465、用户名填完整邮箱、密码填授权码，点「发送测试邮件」
- 只读已采集的数据：采集晚了不会漏（v1.15.0 补发），但会晚一封才收到
- 「不会漏」只对起点之后发表的成立：一个来源第一次进邮件之前发表、又一直没采到的，不算新内容
- 连着失败好几天、或采集停了很久再恢复，下一封会把这段时间没发出去的全补上（多的进附件，补发的也要补译、按条计费）
- 没有 message_id 的帖子，作者一编辑正文指纹就变、按新帖入库（存储层既有规则）—— 新行没发过，发表在上一封窗口里的话会被补发重复一次
- 新主贴不含 Tweakers（一源一串，主题是用户挑好的）；丢了父贴的回复不算新主贴
- 「Tweakers 的 data-datetime 是荷兰本地时间」是推定（服务器端渲染、不带时区），本机 IP 被封，没在真站核实；
  只有 fixture 里的样子（`22-05-2026 17:06`）
- 邮件里不附图片、不放链接、不放舆情（用户要求）
