# 邮件通知：把所选数据源近 N 天的新回复（和新主贴）发到邮箱

> 用户 2026-10-16 提的需求，同一天一起修了「只看新回复」窗口不单调的问题
> （`docs/fixes/2026-10-16-fresh-replies-not-monotonic.md`）—— 邮件里的「新回复」用的就是修好之后的口径。

## 需求（用户原话要点）

- 新增一个菜单，配置：收件人列表；数据源（可多选）；新回复时间（近 3 / 7 / 14 天，**不设置默认是当前时间的前一天**）；
  SMTP 服务器、端口、SSL 端口；发件人邮箱、用户名、密码
- 标题按所选数据源和时间窗口生成
- 正文显示新回复的原文和译文，参考任务详情的显示方式；**不要舆情、不要原文链接**；要体现数据源（如「来自 Facebook 公开小组」）；
  用 HTML 或表格
- 新回复超过 20 条时，以 HTML 文件作附件

## 用户的决定（2026-10-16）

| 问题 | 决定 |
|---|---|
| 「新回复」的口径 | 只看回复时间：近 N 天内发的回复都算，主贴新不新不管（同结果页，3 ⊆ 7 ⊆ 14） |
| 怎么发 | 手动「立即发送」+ 可选每天定时 |
| 新回复缺译文 | 发送前先补译；失败重试，最多重试 3 次；还失败就告知用户，这次不发 |

**v1.15.0：用户让我定的三项（2026-10-17，「你来帮我决定」）**

| 问题 | 我的决定 | 理由 |
|---|---|---|
| 采集之后、发送之前发表的回复会漏发 | **修**：窗口照旧按发表时间，另加补发 —— 没随哪封发送成功的邮件发出去过、发表在这个来源的补发起点之后的，这一封补上，标「补发：之前没发出」 | 通知最怕悄悄漏；采集 08:00、发信 09:00 时每天稳定漏掉一小时，采集间隔越长漏得越多；某一轮失败、服务停一天也一样 |
| 改口径后结果页 / 导出标「新回复」的地方变多 | **接受，不改** | 一个定义处处一致；真实数据没泛滥：便携包数据近 7 天被标 57 条，占 1076 条的 5%（近 14 天 101 条，9%），标签上的「主贴 N 天前」照样分得出老串新串 |
| 没有回复的新主贴不进邮件 | **加进来**，标「🆕 新主贴」，全文照登；它和新回复一样必须翻成才发 | 舆情工具：一条新发的负面帖没人接话，以前就哪封都不出现 |

**v1.16.0：发送前先保证数据是新的（2026-10-20 用户要求）**

用户原话要点：点「立即发送」时，先看所选数据源当天有没有发起过「获取帖子 + 翻译帖子」的任务（不一定要舆情），
没有就自动发起，跑完再判断时间窗口里有没有新回复；要弹确认框让人确认；每天定时规则一样，只是不弹框。

| 问题 | 用户的决定 |
|---|---|
| 怎样算「当天已经有任务」（按数据源分别判断） | 今天 0 点以后，对这个数据源的采集和翻译**都成功完成**的任务才算。失败的、取消的、只采集没翻译的都不算 |
| 确认框给几个选项 | 三个：「先采集再发送」「直接用已有数据发送」「取消」 |
| 自动采集失败怎么办 | **不发送**，发送记录里写明原因（手动时页面上看得到；定时的只在记录里） |
| 停用的数据源 | 不采，只用已有数据（停用的意思就是任务不碰它；这台电脑采 Tweakers 必然 403） |

**v1.17.0：近 24 小时的帖子垫底色（2026-10-20 用户要求）**

用户原话要点：「不设置（近一天）」表示的就是近 24 小时；不管新回复时间选哪个，邮件正文里近 24 小时的帖子（主贴、回复都算）
都垫背景色，一眼看出哪些是近 24 小时的；颜色不要太深太艳。

| 问题 | 我的决定 | 理由 |
|---|---|---|
| 「近 1 天」是不是 24 小时 | 本来就是：从发送那一刻往前推整 24 小时（换到来源的时钟），不按自然日。代码没改，补用例钉住边界 | — |
| 底色垫在哪 | 每条帖子垫自己那一块：主贴是作者行 + 正文，回复是它那一块；卡片不垫 | 底色只表达「这一条是近 24 小时发的」，每条按自己的时间判，不从主贴推到回复 |
| 什么颜色 | 浅绿 `#e8f5e9` | 浅、不艳；邮件里已有蓝（主贴）、橙（新主贴）、灰（补发 / 已发过）几种标签，浅绿和它们都不同色，标签垫在上面照样分得清 |
| 要不要说明底色的意思 | 抬头放一枚同色小标签「近 24 小时发表」当图例，这封里真有垫了底色的帖子才放 | 邮件会发给别的收件人，他们不知道这条约定；一枚标签不是说明段落 |

**v1.18.0：公司内网的自签证书（2026-10-22 用户实测报过）**

用户配公司内网的邮箱（25 端口，不勾 SSL）时，「发送测试邮件」报「证书校验没通过（self-signed certificate），
为了不把密码交给冒充的服务器，没有继续发送」。用户以为是 SSL 端口的问题，并给了同事在别的产品里能发信的 Python 代码。
核对下来两边流程一样：都连 25 端口、都用 STARTTLS 把连接升级成加密。差别只在证书校验：同事的 `smtp.starttls()` 没传 context，
Python 3.12 这时用的是 `ssl._create_unverified_context()`，**完全不校验证书**（查过源码）；这边严格校验，自签证书过不去。
这台开发机解析不了公司内网的域名，没能直接探测那台服务器，判断依据是报错原文里 OpenSSL 给的 `self-signed certificate`。

| 问题 | 用户的决定 |
|---|---|
| 自签证书怎么处理（另两个选项：加「不校验证书」开关；不改代码、请 IT 把证书装进 Windows 受信任根证书） | **只信任这一张证书**：报错时给出证书的 SHA-256 指纹和概况，核对后点「信任这张证书」；之后只认这一张，冒充的服务器拿不出同一张证书 |

提交前评审之后我又定了一条（理由是推断，没法在真服务器上核实）：**可以信任不止一张**。用户的服务器名像是负载均衡，
后面几台要是各用一张自签证书，只认一张就会时好时坏，还报得像有人冒充。每张都得用户自己点「信任」，而且每新信任一张都要重填密码。

## 设计

**配置**存 `app_config`：`notify.settings`（JSON）+ `notify.password_enc`（SMTP 密码密文）。最近一次发送的结果在
`notify_status.last` —— 不能挂在 `notify.` 下，`set_app_config` 按前缀整组覆盖，保存一次配置就会把记录删掉。

**选新回复**（`notify_service.collect_fresh`）：对每个所选来源调 `post_tree.mark_fresh_replies(posts, days, 平铺来源, base=现在)`。
判据与结果页「只看新回复」是同一个函数，只是基准不同：结果页用数据集里最新一帖（报告隔多久打开都自洽），
邮件用发送那一刻（定时摘要要的是「这段时间里有什么新的」）。不设置窗口按 1 天，即从发送那一刻往前推整 24 小时、不按自然日
（2026-10-20 用户明确）。Tweakers 平铺楼层按主题的回复算（`Collector.thread_kind`）。
时间戳不带时区，「现在」要先换到来源的时钟（`Collector.timestamp_tz`）：Facebook 是宿主机时间，Tweakers 是荷兰时间 ——
直接拿上海的现在去比，窗口整体偏 6~7 小时，每天有一段回复哪封都进不去（评审发现）。

**新主贴**（v1.15.0）：近 N 天发的顶层主贴，没有回复也算。判据是「没有父指针、且 `reply_level` 为 0」—— 丢了父贴的回复
也排在树根，但它不是主贴（同结果页徽标）。Tweakers 那种一源一串的来源不出新主贴：主题是用户挑好的那一条，而且只是采到的最早一楼。

**补发**（v1.15.0）：直接记「发没发过」，不拿时间反推。
- `posts.notified_at`：这条帖子（作为新回复 / 新主贴）随一封**发送成功**的邮件发出去的时间，没发过是 NULL。只在 SMTP 投递成功后写
  （作上下文的老主贴不记）；采集不碰它。老库补列后旧行是 NULL —— 升级前本来就没有邮件通知
- 补发起点 `notify_marks.anchors`：{来源: 起点}，起点 = 这个来源**第一次进邮件那一轮的窗口起点**，之后**一直不动**。
  单独一个前缀，写发送记录时不会把它冲掉；取消勾选的来源在保存配置时忘掉起点（再勾回来从那一刻重新算）
- 每一封 = 近 N 天的新内容（窗口照旧）**加上**：发表在起点之后、还没发过的回复和新主贴，标「补发：之前没发出」。
  采集晚了、某一轮失败、采集停了几天、改了天数、事后才读到发表时间，都落在这一条里 —— 起点之后发表的不会漏，
  补发过的也不会再补（它发出去就记了 `notified_at`）
- 窗口内的条目照用户定的窗口每封都列（窗口比发送间隔长时同一条会连着出现几封），前几封已经发过的标「已发过」，读的人好跳过
- 新加进来的来源从这一轮才开始，不补它之前的；起点记录坏了当作没有、就地重起（这一封不补发），不让每一轮都失败
- **写窗口边界的用例要断言条目「不是补发」**：第一封的补发起点就是窗口起点，窗口一旦算窄了，被挤出去的帖子会当补发回到邮件里，
  只看「在不在邮件里」分不出来（v1.17.0 实测：「近 1 天改成按自然日算」这种改坏，起初就这样漏过了用例）
- **补发的翻不成只放原文、照发**：按窗口挑出来的新内容才必须翻成（用户定的「失败就不发」），它们过了窗口会自己掉出去；
  补发的要是也拦邮件，就可能每轮都被挑出来、每轮都失败

为什么这么定：前两版都拿时间去推「这条发没发过」—— 先是入库时间，再是每轮挪动的水位线 —— 三轮提交前评审各找出几种漏法：
失败那一轮窗口里的内容进不去、改了天数算错、重复行合并绕过入库时间、补发没上界时一条拒译的帖子能把邮件永远堵死、
采集停摆比窗口长时「没有新内容」的那几轮把下界挪过头。每修一处就多一层特例；直接记「发没发过」、起点钉死之后这些一起消失，
`upsert_posts()` 这个红线函数也不用动。

**邮件内容**：按来源分节，标题「来自：<采集器显示名>「<来源名>」」；每个讨论串先放主贴（原文 + 译文，超过 600 字截断，
同结果页卡片的折叠长度）作上下文，再列新回复（作者、时间、原文、译文；第 2 层起写「回复 某某」）。
主贴按发表时间从新到旧（同结果页和导出），串里按发表先后。图片只给一行「含 N 张图片」，不附图。
新主贴的卡片标「🆕 新主贴」、全文照登（它是新内容本身，不是上下文）；补发的回复 / 新主贴标「补发：之前没发出」。
**近 24 小时发表的帖子垫浅绿底色**（v1.17.0）：不管窗口选几天，主贴、回复都算，作上下文的老主贴也按同一条判。每条只看自己的发表时间，
基准同窗口（发送那一刻、换到来源的时钟）；`collect_fresh` 给串和回复打上 `recent_root` / `recent`，渲染时主贴单独包一层
`<div class="root">`、回复用它自己的 `<div class="reply">` 垫色，卡片不垫。两种块垫不垫底色内边距都一样、只切换背景色，
同一封信里的卡片不错位（卡片的内边距相应减掉，文字的横向位置和原来一样；纵向每条回复多出几像素，相邻的垫色块才隔得开）。
补发的帖子发表在窗口之外，永远不垫；24 小时内「已发过」的照样垫；附件和正文一样垫。
抬头放一枚同色的「近 24 小时发表」图例，这一份里没有垫了底色的帖子就不放。
所选来源里没有新内容的写「近 N 天没有新回复和新主贴」，但**不进标题**（见下「证据」里的真实数据发现）。
计数分开写：「新回复 X 条、新主贴 Y 条」，标题、正文抬头、各节标题、发送记录都是这个说法。
样式全部内联（邮件客户端常剥掉 `<style>`），帖子内容一律 `html.escape`，换行还原成 `<br>`。
新内容（新回复 + 新主贴）超过 20 条：正文列**最新的** 20 条（结构不变、截过的那节标题注明「正文只列了其中最新的一部分」），
完整内容是一份能用浏览器单独打开的 HTML 附件。「最新」按各来源自己的时钟算发表了多久（v1.17.0 评审发现：以前直接比墙上时间，
荷兰时间的楼层会被当成早了 6~7 小时、挤出正文，那一节还写着「这些比正文里的都早」）。

标题：`【HYXi】<采集器显示名>「<来源名>」[等 N 个数据源] · 近 N 天 · 新回复 X 条、新主贴 Y 条`（为 0 的那项不写），
只点有新内容的来源。前缀不写「新回复」：只有新主贴的那天会自相矛盾（评审发现）；正文抬头是「HYXi 新回复 / 新主贴摘要」，附件名 `hyxi-digest-*.html`。
正文截取时没排进最新 20 条、只因为它的回复排进去才出现的新主贴，在正文里只作上下文（截断），全文在附件里。

**补译**（`_backfill`）：要显示的帖子（新回复、新主贴、作上下文的老主贴）里 `needs_translation()` 为真的，先用 `TranslatorService.execute` 翻，
写回 posts 表。翻完还有失败的就整轮再翻，最多再翻 3 轮（用户定的「最多重试 3 次」）；**新内容**（新回复、新主贴）仍有失败就不发，
`last.message` 写明几条、原因（取译者的第一条 warning，比如模型报的错）。**老主贴翻不成不拦邮件**：它只是上下文，一条总被拒译的老主贴
不能让每天的邮件都发不出去（评审发现）—— 邮件里它只放原文，发送记录里注明几条主贴没翻成。渲染判据同 `needs_translation`，
失败标记不会被当成译文放进邮件。
补译前先 `orchestrator.claim_translation` 占住来源 —— 与结果页补译、任务里的翻译步骤互斥，被占着就每秒重试（最多 30 分钟），
占到后先回库刷新译文（复用 `orchestrator._refresh_translations`）再算还缺哪些，别人刚翻好的不重翻。

**发信**（`deliver`）：`smtplib`。勾了 SSL 连 SSL 端口（`SMTP_SSL`）；不勾连普通端口，服务器支持 STARTTLS 就先升级。
证书用 `ssl.create_default_context()` 严格校验。错误翻成能照着改的人话：535 → 提示不少邮箱要填授权码（不点名哪家），并附服务器原话；
SSL 握手失败 → 端口和 SSL 对不上；超时 / 连不上 → 带上 `host:port`。阻塞调用放进线程（`asyncio.to_thread`）。

**只信任确认过的证书**（v1.18.0，`_connect` / `_pinned`）：
- 先照旧严格校验。过了就照常发，配置里信任过哪些证书都不碍事（IT 后来换上正规证书时不受影响）。
- 没过（`SSLCertVerificationError`）时，校验失败的那次握手里拿不到证书，于是**不校验地再连一次**，读出证书算 SHA-256，
  看配置的 `trusted_certs` 里有没有「这台服务器 + 这个指纹」：有就用这条连接登录发信；没有就关掉连接、抛 `UntrustedCertificate`。
  **比对在登录之前** —— 这条连接不校验证书，不比对就登录，等于把密码交给任何一台冒充的服务器。
- 报错里写明**读到的**证书指纹（每天定时发送失败时，发送记录里只有这句话）。写法 AB:CD:… 和
  `openssl x509 -fingerprint -sha256` 的输出一样（实测）；Windows 证书对话框默认显示的「指纹」是 SHA-1、certutil 打出来是小写不带冒号，
  跟管理员核对时比的是 SHA-256，大小写和冒号不算数（保存时也都认）。说「读到的」，是因为负载均衡后面时再连那一次未必连到第一次那台。
  信任过别的证书时改说「也不是信任的证书」—— 只说确知的，不猜是换了证书还是有人冒充（评审发现）。
- 再连那一次失败（比如 421 连接数超限），或那一次没加密（本机中继拿到明文连接；外部服务器这次没通告 STARTTLS），
  确知的原因还是第一次的校验没过：报错以它为主，再附上第二次的情况。不这样会被翻成「检查端口和 SSL」「请勾选使用 SSL」
  （第一次正是在 STARTTLS 里校验失败的，照着改没用），或者接口直接 500（评审实测过）。
  `smtplib` 的 `ehlo()` 遇到 421 之类不抛异常，只把扩展清空，于是一句「421 连接数超限」会被当成「不支持 STARTTLS」（评审实测过）。
  `_ehlo` 因此检查返回码，不是 250 就带着服务器原话抛出，两次连接、普通端口和 SSL 端口都这样（SSL 端口起初漏了，
  只剩一句「连接断了」，第五轮评审实测出来）；第一次连接被拒时走 `deliver` 的通用分支，
  SMTP 回复一律写成「代码，服务器原话：…」（经 `_server_said` 抹掉密码），不再是 `str(e)` 那种「(421, b'…')」。
  再连那一次对面没出示证书（匿名套件之类）时也照实说，不让一个 `None` 一路抛成 500（这条没有用例：默认的 OpenSSL 造不出这种握手）。
- 指纹直接对证书字节算，概况（主体、签发者、有效期）用 cryptography 尽力解析、解析不了留空：它比 OpenSSL 严，
  有的证书 OpenSSL 照常握手、它解析不了，先解析再算指纹的话这种证书永远信任不了（评审实测过）。解析失败抛的不只 `ValueError`
  （名字里有它不认识的字符串标签时是 `KeyError`），所以一律接住。
- `POST /test` 碰上这种失败时带回 `untrusted_cert`（读到它的服务器、指纹、主体、签发者、有效期）。页面在测试结果下面列出概况和
  「信任这张证书」按钮：点了把「这台服务器 + 指纹」**追加**进表单的信任列表、马上重发一封验证；表单因此算有未保存的修改，
  「保存配置」后「立即发送」和每天定时才用上。已信任时 SMTP 卡片里每张证书一行只读的「服务器 · 指纹」和「取消信任」。
  测试结果连同它测的那个地址一起存，地址对不上就不显示：改了 SMTP 服务器、端口或「使用 SSL」，旧结果连同「信任这张证书」一起隐藏；
  测试请求还没回来时改了地址，回来的结果也不挂到新地址下面 —— 不然点下去信任的是上一个地址的证书（评审发现）。一处判定管两种情况。
  证书概况解析不了时（见上），空的那几行不显示，只留按钮（指纹在报错里）。
  **发送记录里也有「信任这张证书」**：「立即发送」和每天定时撞上没信任过的证书时，记录（`NotifyRun.untrusted_cert`）带上它。
  负载均衡后面时，测试邮件第二次连接可能正好落到已信任的那一台、直接发成功，定时发送碰到的那台就永远加不进来（评审发现）。
  这个按钮只在那张证书属于表单上这台服务器、又还没信任过时出现：改了服务器还点，信任进来的是一条用不上的；
  信任过了还留着，再点就是白发一封测试信。
  报错里的指纹很长、中间没有断行点，测试结果和发送记录都允许在任意处断行，窄窗口里不撑出卡片。
- **新信任一张证书就要重填密码**（`_clean`）：「密码留空 = 沿用已保存的」原来只看服务器和用户名，能调接口的人填上自己那张证书的
  指纹、再冒充这台服务器，就能把已保存的密码引过去（评审在真应用上复现过）。新信任一张 = 认下新的服务器身份；信任过的照旧、取消信任都不用。
  所以密码框空着点「信任这张证书」时，页面会显示「新信任了证书，请重新填写密码」，填上再发。
  重填密码的判据是「有没有以前没信任过的（服务器，指纹）」（集合差），去掉一张、换上另一张也算新信任。
  同一道闸门里，「服务器和用户名没改」也扩成了**密码实际会交给的那一端没变**（`_endpoint`：服务器、实际连的端口、是否 SSL、用户名）：
  已保存的是本机中继时，只改端口就能连到自己在本机监听、不加密的端口，明文收走密码（评审发现，原有缺口）。没在用的那个端口改了不算。
- **每条信任都绑在读到证书的那台服务器上**：`trusted_certs` 存的是 `[{host, fingerprint}]`，`_pinned` 只认「当前 SMTP 服务器 + 指纹」。
  只存指纹的话，给 A 信任的证书换到 B 也放行，握有它私钥的人就能冒充 B、绕过 B 本来有的 CA 校验（评审发现）。
  上一版是「换了服务器就把之前保存的指纹滤掉」，评审实测出死循环：同一台换成 IP 访问后，页面上还列着那个指纹、
  按钮判定已经信任过不再追加，后端又把它滤掉，点多少次都一样。绑定之后，换了地址旧条目自然不生效，同一个指纹给新地址再加一条就行；
  请求在途时改了地址，迟到的结果最多也只信任到旧地址上。
- `trusted_certs` 跟着配置存（指纹不是秘密，进 `notify.settings`）；指纹的冒号、空格、大小写和主机名的大小写都认，
  存成小写、去重；格式不对、没写服务器都 400。最多 10 张（`TRUSTED_CERTS_MAX`），在去重之后数，超了给中文提示
  （接口模型那个 100 只防超大请求）。
- 只认指纹，不看有效期和域名：信任的是「这一张证书」本身，过期不改变它是不是那一张。

**登录被拒后断开，要报出先前那个 535**（`_login`，v1.15.2）：用户在 QQ 邮箱上实测报过
「SMTP 发送失败（smtp.qq.com:465）：Connection unexpectedly closed」，照着这句话什么也改不了。经过如下：
- smtp.qq.com 通告 LOGIN 和 PLAIN 两种登录方式（本机不登录探测过）；
- `smtplib.login()` 第一种被拒后会自动换第二种再试，而对面在拒绝时就断开了连接；
- 第二次尝试撞上断开的连接，抛出「Connection unexpectedly closed」，把真正的 535 盖住了。

现在照旧用 `smtplib.login()`，只在它逐个调 `auth()` 时把每次被拒记下来。登录最终失败时（不论是撞上断开，
还是后一种方式又被拒，比如回个 421 再挂断），有 535 先报第一个 535，没有就报最后一次被拒（同 smtplib）；从没被拒过就断开的，照实报断开。
- **只有 535 才提示授权码**，而且只陈述 535 的含义（服务器认为用户名或密码不对），不说「多半」：SMTP 服务没开启、
  登录太频繁时也可能被这样拒绝（QQ 就是这样），这几种情况一并列出来，但不点名哪家邮箱（v1.15.3 用户要求「QQ 字样都要去掉」）。别的码（454 临时失败、504 不支持这种方式……）只报码和服务器原话，不猜原因。
- 都附上服务器原话。原话合并空白、截到 200 字，为空就写「服务器没有说明原因」。
- 原话里先抹掉密码明文和它的两种 base64 形式（PLAIN 的整串、LOGIN 的单独一段）。有的服务器拒绝时会回显收到的认证串，
  而这句话会进发送记录、显示在页面上，密码只进不出。

评审否掉过两种写法：
- 「登录时一断开就说密码不对」：超时、限流、服务器重启都会被说成密码错，把人支去换授权码；
- 「只试一种登录方式」：去掉了 smtplib 的回退。服务器只认其中一种时，本来登得上的会被报成密码错。

「QQ 回完 535 才断开」是推断，没在真站上实测：报错不带「: timed out」，说明是对面主动断开，和本机复现出的报错一字不差。
要是 QQ 其实一句不回就断开，新提示仍然只会说断开，那时再看。

登录相关的用例 6 条（在 `TestNotifySmtpEndToEnd` 里），替身 `smtp_site` 的 `auth_failure` 参数模拟 6 种服务器表现：
回完 535 挂断、一句不回挂断、454 后挂断、535 之后换方式时 421 挂断、回显认证串、PLAIN 怎么都不认但 LOGIN 能登上。
修复前，「回完 535 挂断」那条复现出的报错和用户看到的一字不差。逐个改坏 7 处，都被对应用例抓到，还原后 sha256 一致：
不优先报 535、只在断开时追溯、不分码一律说授权码、不抹密码、漏抹 LOGIN 形式、不记被拒、只试一种方式。

没处理的（改动前就是这样，这次没动）：
- 登录时读超时报的是 smtplib 的原话「Connection unexpectedly closed: timed out」，不走超时专用提示；
- 用户名或密码里有非 ASCII 字符时，smtplib 编码就失败，报错不是人话。授权码都是英文字母和数字，碰不到。

评审提了、权衡后不改的（第五轮）：
- 「先报第一个 535」可能盖住后一种方式回的更具体的 534 / 454。这和第三轮「535 不能被后面的 421 盖住」正好相反，
  任何固定规则都有反例，保留针对真实 QQ 情形的现状；
- 回显认证串的变体（去掉 `=` 的 base64、被拆成多行）抹不掉。服务器回显认证串本身就是假设情况，变体更牵强，列为残留风险。

**两个入口一条路**：「立即发送」（`POST /send`，后台作业，运行标记同步置上防连点）和每天定时（APScheduler job `notify-daily`，
回调 `notify_service.scheduled_send` 是模块级函数 —— job 存在库里，重启后靠「模块:函数名」找回来）。都走 `_run → _send_digest`。

**发送前先补采**（v1.16.0，`notify_service._ensure_fresh`）：
- 判断：`_stale()` 对每个**启用**的所选数据源，在编排器的任务里找「今天完成、状态 completed、这个来源的
  `collect` 步骤和 `translate` 步骤都 completed」的任务，找不到就要补采；停用的不采、也不列。`GET /precheck` 只读地返回这份名单。
  任务中途被取消时，编排器以前跑完手头那一步又把状态改回 completed（原有缺陷，评审发现），那样取消的就会被当成采过 —— 已改成保持 cancelled。
- 补采：没有要补采的就直接发，不等别的任务。有的话先等正在排队、运行的任务结束 —— 定时采集刚好在跑时，等它跑完它就算今天采过，
  不再重复采一遍；任务还在解析阶段时看不出采哪个来源，所以一律等。等满 `task_timeout_minutes` 还有没跑完的，就不补采、
  这次不发（它可能正采着同一个来源，再起一个就是把真站采两遍）。然后每个要补采的来源各发起一个任务：
  计划 `[collect 该来源, translate zh-CN]`、`scheduled_by="notify"`、描述「邮件通知自动发起：采集并翻译「来源名」」，
  走 `run_task_async`，任务列表里看得到。一个来源一个任务，失败了说得清是哪个；有一个没成功就不发，
  记录写明来源、原因（任务的 `error_message`）和任务号前 8 位。单个任务最多等 2×`task_timeout_minutes`，
  超时就把它取消：这一轮反正不发，别让它接着采、接着付翻译费。采集步骤的参数里带 `source_name`，任务列表靠它显示采了哪个来源。
  任务被取消后手头那一步随后抛异常（采集器不看取消标记，照样跑完、跑挂），状态也还是 cancelled，不会被改成 failed。
- 自动任务用**给定的计划**：`orchestrator.create_task(..., plan=..., scheduled_by=...)`，`execute_task` 见到预置计划就跳过
  `parse_intent` —— 不花一次解析的钱，也不会被模型多加「导出 Excel」「舆情」之类的步骤。来源照样只认已启用的
  （同 `_resolve_sources`）：排队那会儿被停用、被删掉的，任务直接失败、说清原因，采集那一步不跑。
  在任务页重跑这种任务时沿用原计划（按 `scheduled_by=notify` 认），不把描述交给模型重新解析。
- 每天定时发送先让 2 秒（`SCHEDULE_GRACE_SECONDS`）：定时采集设在同一时刻时两个回调同时触发、谁先跑说不准，
  让一让，那边的任务建出来了，下面「先等正在运行的任务」才看得见它，不会把同一个来源采两遍（评审发现）。
- 补采完再挑新回复，基准取补采之后的「现在」：补采那几分钟里发表的回复也算进窗口。
- 入口：每天定时一律 `collect=True`；「立即发送」先调 `/precheck`，有要补采的就弹确认框，
  按用户的选择调 `POST /send {"collect": true|false}`；不带请求体照旧直接发（老调用、测试都不受影响）。
- 进度：`status.progress` 依次是「等待正在运行的任务结束」「正在采集并翻译「X」：<任务当前步骤>」和原有的几步；
  `status.task_id` 是正在等的那个任务，页面据此给出「查看任务进度」链接；发送记录里的 `task_ids` 列出这一轮自动发起的任务。

## 安全

- SMTP 密码 Fernet 加密落库，只进不出（同数据源凭据）；没配 `TWEAKERS_SECRET_KEY` 拒绝保存（400），不降级成明文
- **留空 = 沿用已保存的密码，只限 SMTP 服务器和用户名都没改**：换了服务器还沿用，等于把密码交给那台新服务器 ——
  能调接口的人就能从自己搭的 SMTP 上套出这个「只进不出」的密码
- 外部服务器既不走 SSL、又不支持 STARTTLS 时拒绝登录（密码不明文出本机）；本机回环地址上的中继除外（流量不出这台机器）
- 邮箱地址按发信时的规则校验（正则之外再过一遍 `email.headerregistry.Address`）：只过正则的话，`a[b]@c.d` 这种存得下、
  每次发送却都在组邮件时失败（评审发现）
- 证书严格校验，测试里靠 `SSL_CERT_FILE` 信任现生成的自签证书。被测代码里唯一不校验的连接是 `_pinned` 那一条：
  只用来读出证书比指纹，对不上就关掉，登录永远在比对之后（v1.18.0，用户选的「只信任这一张证书」）。
  密码留空沿用已保存的，还要求**没有新信任证书**：否则填个指纹就能把已保存的密码引到冒充的服务器上（评审复现过）。
  用例里 `SmtpSite(trusted=False)` 不设 `SSL_CERT_FILE`，复刻公司内网那种严格校验必然过不去的服务器
- 用户在对话里给的 QQ 邮箱登录密码**没有使用、没有写进任何文件**：QQ 的 SMTP 要用授权码，而且替用户把别的服务的真实密码填进系统
  不在 Claude 的授权范围内。QQ 实发由用户自己在页面上做

- 定时发送先让 2 秒，等同一时刻触发的定时采集把任务建出来，是尽力而为：调度器忙、补触发晚于 2 秒时，仍可能把同一来源采两遍
- 新来源第一次一条都没采到时，自动任务的翻译步骤会退回去翻别的启用来源里还缺译文的帖子（编排器原有的回退逻辑）
- 「先采集再发送」那一步在真站（Facebook）上由用户验证：E2E 跑在开发库的真数据源上，脚本不点它；链路用本地站点验证过
- 「不会漏」只对起点之后发表的成立：一个来源第一次进邮件之前发表、又一直没采到的，不算新内容
- 连着失败好几天、或采集停了很久再恢复，下一封会把这段时间没发出去的全补上（多的进附件，补发的也要补译、按条计费）
- 没有 message_id 的帖子，作者一编辑正文指纹就变、按新帖入库（存储层既有规则）—— 新行没发过，发表在上一封窗口里的话会被补发重复一次
- 新主贴不含 Tweakers（一源一串，主题是用户挑好的）；丢了父贴的回复不算新主贴
- 「Tweakers 的 data-datetime 是荷兰本地时间」是推定（服务器端渲染、不带时区），本机 IP 被封，没在真站核实；
  只有 fixture 里的样子（`22-05-2026 17:06`）
- 邮件里不附图片、不放链接、不放舆情（用户要求）
- 「近 24 小时」和窗口一样，按来源时钟的墙上时间往前推：有夏令时的来源（Tweakers 按荷兰时间）在切换那一天实际是 23 或 25 小时，
  春季那天个别帖子还可能被标成补发、也不垫色；新内容超过 20 条时，正文挑「最新 20 条」也会差一小时。
  Facebook 按宿主机时间，宿主机是上海时间，没有这个问题
- 抬头的起止时间是宿主机时间，Tweakers 楼层显示荷兰时间、不标时区：对着抬头算会差 6~7 小时，底色看着像判错了（其实是按荷兰时间判的）
- 垫色块里的灰字对比度 4.3:1，略低于 WCAG AA 的 4.5:1（底色浅是用户要求的）；深色模式、低对比度屏幕上底色还看不看得清，没有实机看过
- 父贴缺失的回复当串首时徽标写「主贴」（原有问题，结果页标「回复（主贴缺失）」）
- **公司邮件服务器上的真发由用户做**：这台开发机解析不了公司内网的域名。链路用替身（自签证书 + STARTTLS / SSL）跑通；
  「同事代码里 starttls() 不校验证书」查过 Python 源码，「公司服务器是自签证书」的依据是报错原文
- 第一次信任靠人核对：页面给出的指纹要和邮件管理员给的对上才该点「信任」，代码替不了这一步
- 信任了证书之后每次发信都多连一次（先严格校验、没过再连一次读证书），只多一次握手
- 信任的证书只认指纹，不看有效期：过期了照样发
- 「负载均衡后面几台各用一张证书」是从服务器名推断的，没核实；所以支持信任多张，但第一次撞上另一张时那一封照样发不出去，
  要到页面上点一次「信任」（并重填密码）
- 严格校验失败后为读证书再连的那一次，在负载均衡后面可能连到另一台：报错里给的是「读到的」那张，未必是第一次那台的
- 信任绑在服务器地址上：同一台服务器换个地址访问（比如改用 IP），要给新地址再信任一次；旧地址那条留在列表里，可以「取消信任」
- `POST /test` 会把任意 host:port 上过不了严格校验的证书概况回给调用方，能被拿来探测内网主机的证书信息（原本就看得出通不通）。
  接口对外暴露时必须设 `TWEAKERS_API_KEY`（原有要求）
- 换了端口或「使用 SSL」也要重填密码（v1.18.0 收紧）：以前只改端口时可以沿用已保存的密码
