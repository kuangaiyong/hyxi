# 结果页补译：只采集留下的未译帖子，在结果页上一键补齐

> 起因是用户报「任务 `49f060f0` 的结果页有很多（尚未翻译）」。排查结论是**没有哪一行代码在它的语义下算错**，
> 缺的是一个入口 —— 按 `sdd-fix` 的升格判据升格为 feature（用户 2026-09-15 确认）。

## 背景：为什么会有一大片「（尚未翻译）」

### 现象

- `49f060f0`（2026-09-13，「采集 → 翻译 → 舆情」，全量重跑）当时来源共 306 条，翻译 7 分 25 秒跑完
- 2026-09-15 它的结果页读到的是来源**当前全部 1076 条**，其中 744 条有正文、没有译文。
  `PostContent.vue:42` 在 `translation` 为空、`content` 不为空时显示「（尚未翻译）」

|---|---|---|
| 备份（`49f060f0` 翻译之后） | 306 | 0 |
| 现库里备份就有的 | 304 | **0** |
| 现库里之后新增的（seq 307~1078） | 772 | **744**（另 28 条没正文） |

新增的 772 行全部来自 2026-09-15 的 `b4b9a411`（全量）与 `56757f1c`（增量），计划都只有 `collect` ——
是 v1.12.0 真站验证时 Claude 建的「只采集」任务。v1.12.0 把以前漏采的回复补了回来，新增行里第 2、3 层占 552 行。
这个来源上所有「只采集」任务（9/13 四个、9/15 两个）都是 Claude 为验证采集建的，目的是不花用户的翻译额度。

### 根因

1. **数据**：验证只采集不翻译；v1.12.0 交付报告只写了「306 → 1076 行」，没提醒这批没翻译、会出现在结果页里
2. **设计（既定，不改）**：结果页读来源当前的全部帖子（`orchestrator.py` 的 `load_task_posts()` 按 source_id 查表），
   翻译 / 舆情状态按帖子身份跨任务共享（`hyxi-architecture`：按任务过滤舆情时出过「94 条里 90 条显示未分析」）
3. **缺口**：翻译只在「带翻译步骤的任务」里做（对整个来源增量补齐）。结果页上看不出有几条没翻、为什么没翻，
   也没有舆情页那种增量入口（`POST /tasks/{id}/sentiment`）

### 为什么以前没出现

9/13 下午几轮「只采集」新增过 19 条，当晚 `49f060f0` 翻译时对整个来源增量补齐，一并翻掉了（备份里 306 条 0 条无译文）。
9/15 验证之后，这个来源上再没跑过带翻译的任务。

## 分诊

**feature**：结果页新增「还有 N 条没翻译」的提示与补译入口，外部可见行为变了。

## 我读到的需求

1. [描述] 结果页上不该留着一大片「（尚未翻译）」却没有办法处理 —— 用户选了「结果页加补译按钮」
2. [我的推断] 只翻「有正文、没有译文」的帖子，判据与页面上显示「（尚未翻译）」的条件逐字一致；
   已有译文的一条都不重翻（重翻就是重复花钱）
3. [我的推断] 点之前看得到「还有 N 条没翻译」，N 就是页面上那些标签的条数；翻完之后标签消失
4. [我的推断] 744 条要十几分钟：后台跑、看得到进度，离开页面再回来还知道它在跑
5. [我的推断] 同一批帖子不许被翻两遍：双击、同一来源的另一个任务也点了、带翻译的任务正在跑 —— 重复就是重复花钱

## 待澄清（G1）

1. **译文是「[翻译失败] …」「[翻译为空] …」「[翻译解析失败] …」的帖子，算不算待补译？**
   现状：翻译步骤把失败的也标成已翻译，此后永不重试，页面上显示的是失败标记而不是「（尚未翻译）」。
   两份真实数据里这种帖子都是 0 条。
   - 不算：按钮只管没有译文的，失败标记照旧挂着
   - 算：按钮连它们一起补；任务里翻译步骤的增量判据也得跟着改（否则两个入口口径不一），多一组测试

## 非目标

- **采集后自动翻译**：用户没选 —— 「只采集」就不再省钱，定时采集每轮都花翻译钱
- **结果页改成任务快照**：用户没选 —— 推翻「处理状态跨任务共享」的既定设计
- **舆情补分析**：舆情页已有增量分析按钮
- **舆情详情弹窗里的「(无翻译)」处也放入口**：用户选的入口是结果页

## 设计

每条决策：**选了什么 — 为什么 — 如果错了代价是什么**。

### D1. 补译是结果页上的后台作业，不新建任务

- **选**：`POST /api/v1/tasks/{id}/translate` 起一个后台作业，翻这个任务所读来源里的待补译帖子。
  形状照舆情页的增量分析（`POST /sentiment`）：立刻返回，作业在后台跑
- **为什么**：新建任务要先过大模型意图解析 —— 这次存量处理就得靠防护脚本挡「计划里混进采集步骤」；
  任务列表里也不该为补译多出一条任务
- **错了代价**：补译不进任务列表、没有任务日志，事后只能查应用日志。要改成任务形态得换入口，接口形状不用变

### D2. 「待补译」的判据只有一处

- **选**：`translator_service.needs_translation(post)` = 正文去空白后非空，且译文去空白后为空**或是失败标记**
  （「[翻译失败]」「[翻译为空]」「[翻译解析失败]」开头，G2 改的口径）。`/stats` 的条数、作业挑帖子、
  任务里翻译步骤的增量判据都只用它；失败标记的前缀判断收成 `is_failed_translation()` 一处，译者内部的重试队列也用它。
  `PostContent.vue` 显示「（尚未翻译）」的条件同步改成去空白判断
- **为什么**：提示条上的 N 必须等于页面上「（尚未翻译）」加失败标记的条数；补译按钮和任务里的翻译步骤对「还要不要翻」
  也必须同一个答案。各写一份迟早对不上 —— 本项目「两个出口各排各的，迟早分家」是同一个教训
- **错了代价**：只含空白的正文不再显示「（尚未翻译）」（本来也翻不了）；任务里的翻译步骤从此会重试失败标记
  （以前永不重试）—— 失败原因不消除的话每轮都会再花一次钱，所以 D8 必须一起做

### D3. 每 50 条落库一次

- **选**：作业把待补译的帖子切成 50 条一块，每块交给现有的 `TranslatorService.execute()`，翻完这块就 `save_translations()`
- **为什么**：744 条要 18 分钟左右。整批翻完才写库的话，中途关掉应用（2026-09-15 便携包就被关过一次），
  这一整批的钱就白花了。按块调用现有译者，译者本身一行不改
- **错了代价**：中途失败时一部分有译文、一部分没有 —— 再点一次按钮只补剩下的，这正是按钮的语义

### D4. 同一来源的翻译互斥：补译对补译、补译对任务里的翻译步骤

- **选**：`orchestrator` 里一张来源占用表（source_id → 占用者 id）。补译发现来源被占，返回「正在进行」、不另起一轮；
  任务的翻译步骤发现来源被补译占着，**等它结束、回库刷新译文之后**再算待翻译，翻译期间自己也占着来源
- **为什么**：翻译状态按帖子跨任务共享，同一批帖子翻两遍就是付两遍钱。占用表是普通字典，不用 `asyncio.Lock` ——
  `orchestrator` 是模块级单例，测试每次换一个事件循环，锁一旦在某个循环里发生过争用就绑死在那个循环上
- **错了代价**：带翻译步骤的任务（比如定时任务）可能被一次补译拖住十几分钟，日志里写明在等什么。
  便携包数据里目前没有定时任务

### D5. 只补成功完成的任务，其余一律 409

- **选**：任务状态不是 `completed` 就 409 —— 还在跑的（pending / parsing / running）与**失败 / 取消的**都拒绝
  （后者是交付前代码评审发现的，原口径只挡还在跑的）
- **为什么**：还在跑的，它自己的翻译步骤会处理。更要紧的是 `task["result"]`（连同采了哪些来源）**只在任务成功时写**：
  没记来源时 `load_task_posts()` 会退回「全部已注册来源」，补译就成了把所有来源的未译帖子一起送去翻（按条付费）。
  前端本来就只给已完成的任务显示提示条（D7），接口同一个口径
- **错了代价**：翻译步骤失败的任务（比如跑到一半 API Key 失效）不能在它自己的结果页补译，
  要到同一来源的某个已完成任务的结果页去点，或者重跑任务

### D6. 补译事件走独立频道 `{task_id}:translate`

- **选**：`translation_channel(task_id)` 这个频道上只有两种事件：
  `translation_progress {done, total}`（done 单调不减）与 `translation_complete {status, translated, total, error?}`。
  `translated` 是**真翻成了几条**（按 `needs_translation` 判），不是处理了几条；**一条都没翻成就报 failed 并带上原因**
  （交付前代码评审发现：译者把批量调用的异常吃掉、写成「[翻译失败]」标记，不抛 —— API Key 失效时作业照样报完成，
  页面上 N 纹丝不动、没有任何提示。原因取译者记的第一条 warning，里面有模型回的那句错误）
  译者内部的逐批进度换算成总进度再发；`GET /tasks/{id}/translate/events` 收到 `translation_complete` 就结束
- **为什么**：任务进度流与舆情流共用 `task_id` 频道。同一任务的舆情页正在分析时，翻译进度会串到舆情进度条上
- **错了代价**：多一个 SSE 端点

### D7. 结果页：统计栏下面一条提示条

- **有待补译**：「有 N 条帖子还没有译文」+「翻译这 N 条」按钮。不弹确认，同舆情页增量分析：只翻没翻过的，条数就写在按钮上
- **进行中**：按钮禁用，显示「正在补译 X / N」。进页面时 `stats.translating` 为真也直接显示进行中。
  进度走 SSE，另每 10 秒轮询一次 `/stats` 兜底 —— 翻译可能是共用来源的别的任务发起的，本任务的频道收不到
- **完成**：刷新帖子与统计，N 归零提示条就消失；**失败**：显示原因，按钮恢复（N 是剩下的）
- 任务没完成、或 N 为 0 且没在翻译时，不显示提示条

### D8. 单条重译的两处缺陷（G2 纳入，根因已实测）

补译完的 5 条「[翻译解析失败]」是这样来的：一批里有长帖 → 推理型模型（`deepseek-flash`）把批量预算 4096 烧光、
content 为空 → 整批进单条重译 → 短帖都成了，长帖和「Jup」又失败。

- **长帖**：单条重译 `max_tokens=2048`。2026-09-15 按原参数对 seq 793（3253 字，送 2500 字）真调 1 次：
  HTTP 200、`finish_reason=length`、`completion_tokens=2048` 其中 `reasoning_tokens=2048`、**content 长度 0**
  （推理写了 5509 字还没写完）—— 与 `vision_service` 实测过的同一现象。**选**：单条重译预算提到 8192
  （DeepSeek 非推理模型的上限也是 8K，不会因为超上限整个请求 400）。**错了代价**：8192 仍不够的超长帖照样失败 ——
  交付前在真实数据上补这 5 条验证
- **「Jup」**：单条重译要求译文**超过 2 个字**才算成功（2026-07-29「三阶段全面优化」引入，没写理由），
  「是的」被判失败。**选**：去空白后非空即成功。**错了代价**：模型回一个标点这类垃圾也会被收下（没见过）
- **不改**批量预算：批量失败本来就会落到单条重译，改它只省钱不改结果；本次数据里也没见到「半截译文被当成功」
  （4 个失败批次里其余帖子译文 / 原文长度比 0.38–0.73，原文 ≥ 200 字而译文不到 15% 的 0 条）

## 规格

### R1 待补译条数

- **S1** WHEN 任务的帖子里有「有正文、无译文」2 条，「译文只有空白」「译文是 [翻译失败] …」「有译文」「正文为空」
  「正文只有空白」各 1 条 THEN `GET /stats` 的 `untranslated_count` 为 4、`translating` 为 false
- **S2**（E2E）WHEN 打开有待补译帖子的任务结果页 THEN 提示条上的 N = `untranslated_count` = 出口 `/posts` 里同口径的条数；
  第 1 页「（尚未翻译）」标签数 + 失败标记条数 = 出口第 1 页同口径条数；N 为 0 的任务不显示提示条

### R2 发起补译

- **S3** WHEN `POST /translate`，有 3 条待补译，模型已配置 THEN 返回 `{status: started, pending_count: 3}`；
  作业结束后这 3 条有译文、`translated` 为真；发给模型的条数合计 3；已有译文逐字不变；没正文的仍为空
- **S4** WHEN 没有待补译的帖子 THEN 200 `{status: completed, pending_count: 0}`，不调模型、不占来源
- **S5** WHEN 模型没配置 THEN 400，`detail` 含「请先配置 LLM API」，不起作业 —— 不许先回「已开始」再在后台静默失败
- **S6** WHEN 任务状态不是 completed（pending / parsing / running / failed / cancelled）THEN 409，不起作业、不占来源
- **S7** WHEN 来源已被占着（本任务或共用来源的别的任务在补译）THEN 200 `{status: running}`，不发任何翻译请求
- **S8** WHEN 任务不存在 THEN 404

### R3 分块落库

- **S9** WHEN 待补译 3 条、块大小 2，第二块的翻译请求被卡住 THEN 这时库里第一块的 2 条已有译文、第 3 条还没有；放行后全部翻完

### R4 进度流

- **S10** WHEN 连着 `/translate/events` 发起补译 THEN 收到的 `translation_progress.done` 单调不减、最后等于 total，
  最后一个事件是 `translation_complete {status: completed, translated: 3}`，流随之结束
- **S11** WHEN 补译在跑 THEN `task_id` 频道（任务进度流、舆情流共用）收不到任何事件
- **S12** WHEN 作业自己失败（例如跑起来才发现模型没配置）THEN `translation_complete {status: failed, error}`，来源随即放开
- **S19** WHEN 模型每个请求都报错（替身让每个请求都回 400）THEN `translation_complete {status: failed, translated: 0}`，
  `error` 里带着模型回的那句错误

### R5 与任务里的翻译步骤互斥

- **S13** WHEN 补译在跑，一个带翻译步骤的任务开始翻译同一来源 THEN 它等补译结束再算待翻译：
  两边合计发给模型的条数 = 待补译条数，任务照常完成
- **S14** WHEN 任务的翻译步骤正在翻某个来源 THEN 对这个来源发起补译返回 `{status: running}`，不另发翻译请求

### R7 单条重译与失败标记（D8）

- **S16** WHEN 批量翻译返回空内容、单条重译对「Jup」回「是的」THEN 译文是「是的」，不是失败标记
- **S17** WHEN 模型预算低于 2049 token 时只推理不出字（按 2026-09-15 实测复刻），一条长帖的批量返回空内容
  THEN 单条重译拿到译文，不是失败标记
- **S18** WHEN 库里有一条译文是「[翻译解析失败] …」、已标已翻译，一个带翻译步骤的任务跑增量 THEN 这条被重新翻译、失败标记被替换；
  已有正常译文的一条都不发

### R6 结果页（E2E）

- **S15** WHEN 点「翻译这 N 条」THEN 出现「正在补译」、按钮禁用；完成后提示条消失，这一页不再有「（尚未翻译）」，
  `/stats` 归零（这一条会真的调模型，默认不跑，`E2E_BACKFILL_CLICK=1` 才跑）
