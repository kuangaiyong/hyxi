# 一源一串的论坛结构：主题 + 平铺回复 + 引用块

> 采集侧的故障（140 条楼层被当成 140 个主贴）与真站实测记录见
> `docs/fixes/2026-09-19-tweakers-floors-treated-as-topics.md`。
> 两者一起交付：呈现的前提是采得到、归属对。

## 分诊

- **修复**：一个 Tweakers 来源显示成 140 张「主贴」卡 —— 现有行为与预期不符
- **新功能**：引用块要能看见（引用了谁、基于哪段内容）、引用里的图要采到且归属正确 ——
  外部可见行为变了

## 我读到的需求

1. [描述] Tweakers 没有「主贴 + 回复贴」这种说法，是类似朋友圈的方式：
   一个人发主题，大家基于主题评论，有人再引用别人的话评论
2. [描述] 呈现要看得见「发表了什么主题 / 大家基于主题回复了什么 / 又基于哪些内容做了引用回复」
3. [描述] 涉及的图片都要采到，不能缺失，也不能张冠李戴
4. [描述] **红线**：不能影响 Facebook 公开小组数据源的正常使用

`thread_of()` / `fresh_reply_count` / 层级缩进这一整套都是为 Facebook 写的。
Tweakers 要的不是「另一棵嵌套树」，而是**一条主题 + 一层回复 + 引用框**。

## 冻结后的口径（已与用户确认）

| 问题 | 口径 |
|---|---|
| 引用的呈现 | **主题 + 平铺回复**；引用以「引用框」嵌在引用者那一条里（与原站一致）。不做嵌套树、不做缩进挂靠 |
| 存量数据 | 不做 DB 迁移，靠一次全量重跑（引用只有回源才有） |
| 真站核对 | 本机真 Chrome 直连可达，交付前跑一轮真站 |

## 设计

每条决策：**选了什么 — 为什么 — 错了的代价**。

### D1. 主题 = 显示第 1 页的第一条 `.message`；其余楼层一律 `reply_level=1`

- **选**：脚本抓到第 1 页时，主题就是该页 DOM 顺序里的第一条；该页其余楼层与后续所有
  页面的楼层，一律 `parent_fingerprint = 主题指纹`、`reply_level = 1`。
  **不用 `.message.topicstarter` 认主题**
- **为什么**：这就是原站的结构（实测 `/0` 第一条就是发起帖，正文与 `<h1>` 标题吻合）。
  `build_tree()` / `order_by_thread()` 本来就支持任意深度，一处都不用改。
  那个 class 实测标的是「这条是发起人写的」—— 第 1 页 15 条都带，照它认主题会认出一堆
- **错了的代价**：站点改版把某条置顶（公告/精选）时主题会指错。缓解：脚本把
  「认定为主题的那条」的用户名/时间/正文前 60 字打进任务日志，真站跑一轮一眼可核

### D2. 增量跑的主题指纹由 Python 从库里下发

- **选**：`Collector` 增声明 `thread_kind`（`"thread"` = 一源一串；默认 `"feed"`）。
  `CollectorRunner` 在 `thread_kind == "thread"` 且增量时把
  `storage.thread_topic_fingerprint(source_id)` 塞进 source，`build_job()` 透传为
  `job.topic_fingerprint`
- **为什么**：增量从 `max_page_number + 1` 起抓，脚本根本看不到第 1 页，而父指针需要
  一个真实存在的指纹
- **判据**：`parent_fingerprint` 为空且 `reply_level = 0` 的行**恰好一条**时返回它；
  0 条或 >1 条返回 `None`
- **为什么不用「page 1 里时间最早那条」**：存量库是 140 条并列主贴，启发式会挑一条
  普通楼层当主题，然后新楼层全挂到它下面 —— 页面看着像对的，实际每个串都错
- **错了的代价**：多 root 状态下增量跑的新楼层没有父指针（仍是 root），日志明说原因
  和解法；不写坏任何数据

### D3. 引用作为**独立快照**存，绝不并进 `content`

- **选**：`posts` 新增 `quote_json`，放采集器抓到的
  `{message_id, cite, username, content, truncated, images}`；`content` 一个字符不动
- **为什么**：`makeFingerprint()` 吃 `username|timestamp|content[:100]`，把引用并进
  `content` 会让**全部历史数据失配**、已翻译的帖子被判成新帖重新付费翻译。原站本来
  也是「引用框 + 正文」两块
- **错了的代价**：库里同时存在引用快照和被引用楼层自己的正文两份相近文本 ——
  **有意为之**：快照是「引用发生那一刻的原文」，且是被引用楼层没采到时**唯一**的内容
  （实测 `large-quote` 被服务端截断、点不开）。出口一律优先用被引用楼层自己那份

### D4. 出口用 `message_id` 把引用解析到被引用楼层

- **选**：`/posts` 出口按 `(source, message_id)` 建索引，解析成功时用**那条楼层自己的**
  `username` / `timestamp` / `content` / `translation` / `images`，置 `resolved=true`；
  解析不到用快照，置 `resolved=false`
- **为什么**：实测 94/97 带被引用楼层 id；**只有这条路拿得到全文**（截断点不开）；
  **也只有这条路能保证引用图不缺不错** —— 那些图本来就是那条楼层自己的 `images`
- **解析在出口做、不落库**：落一份指纹就是双写，而且指纹会被 `post_aliases` 归并
- **错了的代价**：被引用楼层不在采集范围内时引用框只显示截断快照，UI 明说
  「引用片段（原楼未采集）」

### D5. 引用图从 `[Afbeelding]` 锚点取，走独立文件、不进正文图清单

- **选**：引用图两路来源 ——（a）引用块里文本为 `[Afbeelding]` 的 `<a href>`；
  （b）引用块里过了渲染尺寸线的 `<img>`。落成 `<指纹>_q<引用序号>_<图序号>.<ext>`，
  写进 `quote.images`
- **为什么**：真站上被引用的照片**不是 `<img>`**，尺寸过滤这条路用不上；而引用块里
  普通 `<a>`（指向别的页面、用户相册）不是图，不能误收
- **为什么把 `<img>` 那一路也收进来**：真站上引用块里的 `<img>` 目前只有 16×16 表情
  （被尺寸线挡掉），但照片真被渲染成 `<img>` 时它同样属于被引用者 —— 收了是「不缺失」，
  归属仍在引用框里，不是张冠李戴
- **错了的代价**：引用块里「手动贴的图片链接」若文本恰为 `[Afbeelding]` 会多下一张图；
  日志里逐条报候选地址，能看出来

### D6. **一条楼层引多人**，所以引用是数组

- **选**：`posts.quotes_json` / `PostData.quotes` 存**数组**，出口逐条解析、前端逐条渲染、
  导出逐条列出（`｜` 分隔）
- **为什么**：真站实测串 2336074 第 1 页就有一条楼层引两个人的写法（先引一条带
  messagelink 的、再引一段没有链接的）。原来的「一条帖子最多一个引用块（实测 97/97）」
  是**在抽查样本上成立的前提，不是站点规律** —— 只取第一条就是静默丢掉一段被引用的内容，
  页面上完全看不出来
- **错了的代价**：存储与出口多一层数组，改动面比单对象大。这笔代价换来的是不丢内容

### D7. 图片一律让**浏览器**取，不开第二条通道

- **选**：`loadLazyImages()`（整页滚一遍触发懒加载）+ `prefetchQuotedImages()`（为
  `[Afbeelding]` 锚点建游离 `Image`）。`context.request` 的回源只作为最后兜底
- **为什么**：真站实测不滚动时一页 100 层楼里 13 张正文图**只加载了 1 张**，其余全走回源；
  而回源那条路一轮连打十几次会被 WAF 挡掉一批（实测 16/35 张 403）—— **表现是「图静默缺失」**，
  页面和日志上都看不出来。滚到底之后 13/13 由浏览器加载；引用块里的图浏览器**永远不会请求**
  （它们是 `<a href>`），必须显式建 `Image` 拉一把
- **为什么这也符合反爬虫姿态**：请求数从「页面加载一次 + 回源一次」减成「只加载一次」，
  而且全部走页面自己的网络栈（同一套 cookie、指纹、代理）
- **错了的代价**：整页滚动让每页多花几秒（步长 1200px、120ms）。图本来就该被读者加载出来，
  这不是额外流量

### D8. 引用图**不进多模态理解、不进舆情**

- **选**：`vision_service` 只吃 `post.images`，不吃 `quote.images`
- **为什么**：引用图属于**被引用者**。算进引用者的图片描述等于让模型以为
  「这个人在晒这张图」—— 正是用户说的张冠李戴。而被引用楼层若在采集范围内，
  它自己的图早被描述过了
- **错了的代价**：引用到**未采集楼层**的图只有人看得见、模型看不见。
  数量极小（本串 100 楼里 6 处）

### D9. 结果页按 `thread_kind` 选措辞，前端不认 collector_id

- **选**：`PostData` 增 `thread_kind`。`"thread"` → 徽标「主题」、回复区「N 条回复」、
  页头「共 N 个主题」；`"feed"` → 仍是「主贴 / N 条评论与回复」（**一个字都不变**）
- **为什么**：用户明确说「不能是主贴回复贴那种」。「主贴」是 Facebook 小组的语汇，
  用在一串 Tweakers 上会让人以为那里有 140 个独立帖子。
  站点知识留在 `Collector` 声明里，前端不会长出 `if (source === 'tweakers')`，
  加一个新来源时前端零改动
- **错了的代价**：措辞不合口味，改一个映射表即可

### D10. 引用框渲染在正文**上方**，只显示、不折叠

- **选**：`PostContent.vue` 在正文之前渲染引用框：`引用 @<名字> · #<序号>` +
  被引用正文（跟随「双语/只看译文/只看原文」）+ 被引用图（点开灯箱）；
  其下才是引用者正文。`#<序号>` 做成指向 `#post-<序号>` 的锚点
- **为什么**：实测引用块就是 `.messagecontent` 的第一个子元素，原站也长这样。
  整串只剩一个 root，所有楼层都在同一张卡里，锚点跳转可行
- **错了的代价**：无 —— 没有引用的帖子渲染结果与改造前逐像素相同

### D11. 导出：**只有报告里真有引用时才加「引用」列**

- **选**：`EXPORT_COLUMNS` **不动**；新增 `export_columns(rows)`：行里没有任何引用时
  返回原样的列定义，否则返回插了 `("quote", "引用")` 的副本。`/export` 两处
  （csv writer + `build_export`）都用它
- **为什么**：这是让「Facebook 零可见变化」成立的唯一做法 —— Facebook 的报告里一条
  引用都没有，那一列**根本不会出现**，列集合与改动前完全一致
- **错了的代价**：CSV 的列数随数据而变（表头行始终写出）。要固定形态就恒加该列，
  代价是 Facebook 报告多一列全空

### D12. 不改舆情 prompt 结构，但要知悉成本变化

- **选**：不动 `sentiment_service`。修好父指针后 `thread_of()` 把整串 203 楼当成一个
  讨论串，每条楼层的分析带上最多 `THREAD_CONTEXT_LIMIT = 3000` 字同串上下文
- **为什么**：这正是修复目标（改造前每条楼层都是零上下文判正负），且该机制本来就是
  给 Facebook 写的，不是新东西
- **错了的代价**：Tweakers 单次舆情任务的花费与时长上升。`THREAD_CONTEXT_LIMIT`
  保持不动 —— 改它会影响 Facebook（红线）；真觉贵再单开一题

### D13. 顺带补上 Tweakers 的 `post_url()`

- **选**：`{base}/forum/list_message/{message_id}#{message_id}`（真站实测形态），
  并做与 Facebook 同款的 `http(s)` 前缀校验 + 非字符串防御 + 路径段编码
- **为什么**：改造前 Tweakers 一条链接都没有（基类默认返回 `None`），结果页上
  Tweakers 的主题卡是唯一没有原帖入口的卡片
- **错了的代价**：站点改 URL 形态 → 链接 404。现算的，改一处

## 规格

### R1 串结构

- **S1** WHEN 采集第 1 页 THEN `/0` 第一条 `.message` 是主题（父指针空、`reply_level=0`），
  该页其余楼层父指针指向它、`reply_level=1`
- **S2** WHEN 采集第 2..N 页 THEN 全部楼层父指针指向主题、`reply_level=1`
- **S3** WHEN 增量跑且 `start_page > 1` 且库里恰好一个 root THEN job 带
  `topic_fingerprint`，新楼层挂上去
- **S4** WHEN 库里 root 数 ≠ 1 THEN job 不带主题指纹，脚本打出含「全量重跑」的警告，
  整轮照常成功
- **S5（拒绝路径）** WHEN 用户从第 3 页起抓且库里没有第 1 页 THEN 不臆造主题，同上打警告
- **S6** WHEN 一条楼层正文只有引用、正文为空 THEN 仍入库（`message_id` 非空 ⇒
  `drop_empty_posts()` 不丢）

### R2 引用采集

- **S1** WHEN `.messagecontent` 的直接子元素里有 `<blockquote>` THEN 该楼层 `content`
  **不含**引用正文（与黄金基线逐字相等），`quotes` 被填
- **S1b** WHEN 一条楼层有**多个** `<blockquote>` THEN **每一个**都进 `quotes`（真站实测有这种）
- **S2** WHEN 引用块里有 `a.messagelink` THEN `quote.message_id` = href 里的
  `list_message/<id>`，`cite` = 锚点原文，`username` = `cite` 中 `" schreef op"` 之前的部分
- **S3** WHEN 引用块里**没有** `a.messagelink` THEN `message_id` / `cite` 为空，
  `content` 照抓（实测 3/97）
- **S4** WHEN `.large-quote` 且正文含字面量 `[...]` THEN `truncated=true`
- **S5** WHEN 引用块里是 `<img>`（表情 / 照片）THEN 不算引用者的正文图
- **S6** WHEN 引用块的 `[Afbeelding]` 锚点或过了尺寸线的 `<img>` THEN 地址进对应那条引用的
  `images`（`<指纹>_q<引用序号>_<图序号>.<ext>`），**不出现在 `post.images`**
- **S8** WHEN 页面上的图是懒加载的 THEN 滚一遍整页让浏览器加载；`[Afbeelding]` 锚点则建游离
  `Image` 拉进来 —— 不让它们走回源那条会被 WAF 403 的路
- **S7** WHEN 引用图落盘失败 THEN 只跳过这一张，帖子照常入库

### R3 存储与出口

- **S1** WHEN 写入带 `quote` 的帖子 THEN `quote_json` 落库，读回逐字段相等
- **S2** WHEN 全量重跑遇到已存在帖子且本轮没抓到引用 THEN 不把已有 `quote_json` 冲空
- **S3** WHEN 全量重跑 THEN `seq` / `translation` / `sentiment_at` 一律不动
- **S4** WHEN `GET /posts` THEN 带 `quotes` 与 `thread_kind`；能找到被引用楼层时
  `resolved=true` 且 `index` = 那条楼层在扁平数组里的 1-based 位置
- **S5** WHEN 找不到被引用楼层 THEN `resolved=false`，取快照，`index=null`
- **S6** WHEN 帖子没有引用 THEN `quotes` 为空数组
- **S7** WHEN `thread_topic_fingerprint(source_id)` THEN root 恰好一条时返回其指纹，
  否则 `None`

### R4 呈现与导出

- **S1** WHEN `thread_kind == "thread"` THEN 徽标「主题」、回复区「N 条回复」、
  页头「共 N 个主题」
- **S2** WHEN `thread_kind == "feed"` THEN 文案与改造前逐字相同
- **S3** WHEN 一条回复带 `quote` THEN 引用框在正文上方，显示被引用者、正文、图；
  `resolved` 时显示 `#序号` 锚点
- **S4** WHEN 引用未解析 THEN 标「引用片段（原楼未采集）」；`truncated` 另标
  「原站只提供截断片段」
- **S5** WHEN 报告里一条引用都没有（**Facebook 全部场景**）THEN 列集合与改造前完全一致
- **S6** WHEN 报告里有引用 THEN 多出「引用」列且有值；一条楼层引多人时逐条列出
- **S7** WHEN 搜索 THEN 命中 `quote.content` / `quote.username` 时该楼层算命中

## 非目标

- **不写存量数据迁移**：引用只能靠回源（长引用被服务端截断、点不开），DB 迁移填不出来；
  且「page 1 第一条」这条启发式在真实历史数据上会选错主题
- **不点 `.toggle-quote`**：实测点了没用（文本长度一个字符都不变、0 个新 XHR）
- **不解析荷兰语日期**：`quote.timestamp` 只取自解析成功后的被引用楼层
- **不给回复挂「🔗 原帖」**：判据在 `_post_url()`，两个平台共用一个口径
- **不翻译引用快照**：解析到楼层时用的是那条楼层早就翻好的译文；只有引用到串外/未采到
  的楼层时才会显示荷兰语原文，UI 明说「这一段尚无译文」
- **不按来源调 `THREAD_CONTEXT_LIMIT`**（D10）
- **不加串标题（`<h1>`）**：真站上有，但要新开一列 + 迁移 + 出口 + UI，属装饰性增强
