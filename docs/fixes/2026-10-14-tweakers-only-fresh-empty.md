# Tweakers 任务「只看新回复」3 / 7 / 14 天都是空的

## 现象

用户反馈：数据源是 Tweakers 论坛的任务，结果页点「🔥 只看新回复」，不管选近 3 天、近 7 天还是近 14 天，
都显示「近 N 天内没有老帖收到新回复」，而实际上有新回复。

**这个开关对 Tweakers 从来没有生效过。** 导出报告里的「老帖新回复」也是同一个原因：
总览恒为 0 条、明细「更新提醒」列恒为空、「近期新回复」表从来没被建出来。

## 复现（修复前的代码，2026-10-14）

开发库副本（SQLite backup API 拷出，副本里停用了 Facebook 来源）+ 本地 fixture 站点
`backend/tests/fixtures/fixture_site.py 8899`。注册一个 Tweakers 来源指向它，用**真 `tweakers.js`**
（真 Chrome、真 HTTP）采了一轮：3 页 9 楼，22-05-2026 17:06 … 27-05-2026 12:00。

> 采集是直接调编排器 collect 步骤用的 `CollectorRunner.execute` 跑的，**绕开了意图解析**：
> 开发库里那个 LLM 账户返回 `402 Insufficient Balance`，任务在解析这一步就失败了。
> 意图解析与这个 bug 无关，产出的楼层与任务流水线里那一步完全相同。

入库的 9 楼（只读查的副本）：**父指针全部为空、`reply_level` 全部为 0**，时间都是荷兰格式。

| 查询 | 结果 | 应该是 |
|---|---|---|
| `/posts`（不筛选） | 9 张卡片 | 9 |
| `/posts?only_fresh=true&fresh_days=3` | **0** | 5（24-05 15:47 起的 5 楼都在最新一楼 27-05 12:00 的 3 天内，主题在 22-05） |
| `fresh_days=7` / `14` | 0 / 0 | 0 / 0（这串总共才 5 天，整串都在窗口里，按既定规则不标） |
| `/export?format=xlsx&fresh_days=3` | 工作表只有「概览、帖子明细、配图」；总览「近 3 天老帖新回复 0 条」 | 有「近期新回复」表，5 条 |

## 根因

**`collectors/tweakers.js` 一个 `parent_fingerprint` / `reply_level` 都不写**，每一楼都按主贴入库。
而「老帖新回复」的判据 `post_tree.mark_fresh_replies()` 只认有父贴的回复，第一句就是
`if not post.get("parent_fingerprint"): continue` —— Tweakers 一条都认不出来，结果恒为空集：

- `/posts` 的 `only_fresh` 拿空集去筛主贴 → 一条不剩
- 导出 `_export_rows()` 的标记同样为空 → 总览 0 条；「近期新回复」表由 `ExcelService._fresh_threads()`
  生成，它只把 **level > 0** 的新回复挂到主贴下，Tweakers 楼层全是 level 0，即使判据修好了这张表也建不出来

排除了另一个可能：时间格式。分支 `feat/tweakers-thread-quotes` 上 2026-09-19 的真站实测记录确认
`data-datetime` 就是 `22-05-2026 17:06`，`parse_time()` 认得（复现数据里同样如此）。

**测试一直是绿的**：`TestOnlyFreshFilterEndToEnd` 把来源标成 `collector_id: "tweakers"`，造的数据却带父指针 ——
替一个真实不存在的数据形状作证。

## 修法

不改采集和存储（那是分支上的结构性修复：采集端给楼层补父指针、存量需全量重跑；用户已明确开发在 main 上、
不动那个分支）。只在出口的判据层修，存量数据立即生效：

| 层 | 改动 |
|---|---|
| `Collector.thread_kind` | 新声明 `"feed"`（一个来源许多主贴，Facebook）/ `"thread"`（一个来源一条主题 + 平铺回复，Tweakers）。名字和取值沿用分支，日后合并只有注释上的小冲突 |
| `post_tree.flat_thread_starts()` | 一源一串、且**一条父指针都没有**的来源 → 它的主题楼层：**时间最早**的那一楼（不能按 seq / 页码挑 —— 分支实测真实存量库里主题排在第 63 条） |
| `post_tree.mark_fresh_replies(..., thread_sources)` | 平铺楼层算作主题的回复，其余判据一字不改：回复时间 ≥ 截止点且主题时间 < 截止点；主题自己永远不标；整串都在窗口内不标；时间读不出不标。有父指针的来源照旧走原来那条路 —— 分支合并、全量重跑之后，这条兜底自然不再走 |
| `results._thread_sources()` | 来源 → 采集器声明，注册表为准、来源被删后用任务里记下的 `collector_id` 兜底；外加历史数据缺省的 `"tweakers"`（多来源改造前的帖子没有 source 字段，全链路按它处理）；`/posts` 与导出两处调用都传它 |
| `results._export_rows()` | 平铺来源的每一楼（含主题自己）带隐藏字段 `thread_root`（主题那一行的下标），不进任何一列 |
| `ExcelService._fresh_threads()` / `_older_reply_count()` | 按 `thread_root` 把新楼层挂到主题下、数「另有 N 条较早回复」—— 平铺楼层不排在主题下面（主题按时间沉在最后），「数到下一个 level 0 为止」数出来恒为 0 |
| `results._export_meta()` | 概览的评论数把平铺楼层算进去（主题之外的每一楼）—— 否则同一张表里「评论 0 条」紧挨着「老帖新回复 N 条」 |

前端不改（用户定的）：被筛出来的楼层卡上不加 🔥 标记。

### 代码评审（9 条，无严重级）

| 发现 | 结论 |
|---|---|
| 历史数据缺省 source 为 `"tweakers"`，`_thread_sources` 收不到它 | **修**。从库里读出的帖子一定带真实来源 id（两个写入口都用参数里的 id），但 `/posts` 优先用任务内嵌的 `result.posts`，历史格式的那批不带 source —— 补了用例 |
| 「另有 N 条较早回复」对 Tweakers 恒为 0 | **修**（`thread_root` + `_older_reply_count` 的平铺分支） |
| 概览「评论 0 条」与「老帖新回复 N 条」自相矛盾 | **修**（`_export_meta` 把平铺楼层算作评论） |
| 主题按最早一楼认，没采第 1 页 / 主题时间读不出会认错 | **已知限制，不修**：Tweakers 的表单字段里没有 `start_page`、LLM 给的会被忽略，首轮全量必从第 1 页起；真站楼层都有 `data-datetime` |
| 来源里一出现父指针，平铺兜底就整体失效（混合状态） | **不成立**：分支在认不出主题时不猜、新楼层同样平铺；全量重跑后整串都结构化，走原判据 |
| 平铺楼层的新回复既是 level 0 又挂到别人下面，后面紧跟的 level > 0 新回复会挂错 | **不成立**：`order_by_thread` 先序输出，level > 0 的行一定紧跟在自己的祖先后面，平铺楼层没有子帖 |
| 改成在出口统一给平铺来源虚拟补父指针 | **不采纳**：会把结果页从「一楼一张卡」改成「一张主题卡 + 回复」，与用户定的最小化范围冲突；结构性修复在分支上 |
| `_export_rows` 里主题算了两遍；`_thread_sources` 与 `_source_names` / `_url_sources` 写法重复、多查一次来源表 | 不改：结果不受影响，按最小化原则不动既有代码 |
